# FN09 원자료 재사용과 후속 합성 START 상세 계약 후보

상태 `DRAFT / NOT_ADOPTED / SOURCE_GO0`. PMO 결정 :31은 상세 설계만 허용한다. 부모는 [환경 현재성 검토](FN09_POLICY_HANDOFF_CURRENTNESS_REVIEW_20261107.md) `E7F4412B786F88D6B7EF8ECAB344EFB918B9EC9491BB80E88B8763AE7BF02FFA`와 [구현 통제 §412](FN06_IMPLEMENTATION_CONTROL_20261104.md#412-다음-fn09-발급현재-사실-연결의-계약-후보-구체화)다. 기존 A안의 동결 5파일과 409·412 관측을 기준 증거로 보존한다. 실제 DB·권한·키·서비스·Agent·SDK 실행과 코드 변경은 이 문서의 범위에서 제외한다.

## 1. 적용 대상과 선택

P1에서 등록한 불변 원자료 S와 예약 Q의 원래 fullref·bytes·P1·Session·H·제어·수명을 유지한다. 현 P2 아래에서 같은 담당자와 클라이언트가 같은 임무를 잇는 **특정 명령 ID의 후속 합성 START 한 건**에 한해 재사용을 승인할 수 있다. 원 환경을 계속 조회하면 기존과 같이 `CHANGED/POLICY_CHANGED`가 표시된다. 제안하는 판정은 내부 `FN09_ORIGIN_REUSE_SYNTHETIC_START_V1` 소비 전용이다. 실제 실행 허가, SDK 세션, OS writer, E 발급, 외부 전송 권위 및 기존 단계의 실행 상태는 이 판정에서 도출되지 않는다. Q는 계속 `RESERVED_NOT_ISSUED`다. 합성 큐의 기존 `SYNTHETIC_ONLY`, `HELD_SYNTHETIC_ONLY`, `executionAuthorized:false`, `dispatchPerformed:false`를 유지한다.

현행 A안의 정책 참조 교체만으로는 환경 보호 검사에서 412가 발생한다. P2로 새 환경과 준비를 만드는 대안은 fullref와 원 실행 ID가 달라지고 담당 연결을 별도로 전환해야 한다. 상세화는 원자료 보존 경로를 선택하고, 새 준비 경로는 부모 §3의 대안으로 남긴다.

## 2. 공개 명령과 결정 주체

1. 요청자는 원 S의 동일 활성 HUMAN과 client·Session·H·controlGeneration을 가진 프로젝트 OWNER다. 보호 원자료 화면 또는 합성 호출자가 exact S/Q를 선택하고, 새로운 후속 명령 UUID 한 개와 만료·사유·위험·복구 설명을 고정한다. 서버는 P2의 기존 `requestApproval` 명령 허용, 현재 제어·재인증, 별도 소스 보호와 §3 재검증을 모두 적용한다. 결정은 현재 `ProjectApprovals.decide`의 동일 사용자·동일 client·동일 제어 방식에 따라, 동일 Session/H의 OWNER가 P2의 `decideApproval` 허용과 유효한 재인증으로 명시 `APPROVE`한다. 요청과 결정의 명령 UUID는 후속 START UUID와 각각 달라야 한다. connector, 시스템 자동 판정, 보관된 P1 승인, 다른 사용자나 새 Session이 이를 대행하지 않는다. `REJECT`와 `REQUEST_CHANGE`는 기존 상태로 종료되며 해당 결정으로 START를 소비할 수 없다.
2. 제안하는 기존 `POST /api/v1/projects/:projectId/commands`의 한정 확장은 `requestApproval`에서 exact `{details,candidatePayload}`의 START 재사용 목적을 받는 것이다. `details`의 기존 여섯 키를 유지한다. `details.actionScope`는 기존 열 키, `operation='queueExecutionCommand'`, `targetRef=null`, `expectedVersion=0`, `baselineRefs=[]`, `environmentRef=null`, `sourceScopes=[]`, `limitsRef=null`, 실제 HUMAN의 `requestedSubjectRef`와 `controlGeneration`이다. 빈 공통 키와 별개로 환경·소스·한도는 §4의 서버 저장 증거에 결박한다. `candidateCommandId`는 후속 START 명령의 UUID이며 `payloadHash=SHA256(canonicalJson(candidatePayload))`다. `requestApproval`·`decideApproval` 외피의 `approvalRef`는 null이다. 결정 입력 `{requestId,expectedVersion,scopeDigest,decision,reason}`는 유지한다.
3. `candidatePayload`와 최종 큐의 `payload`는 기존 `execution-commands.ts`의 정확한 일곱 키와 선택적 `originReuse:{originRef,reservationRef}` 하나를 더한 이 목적의 정확한 여덟 키다. `operation='START_SESSION'`이며 내부 `payload:{contextBundleRef,optionsRef}`는 그대로다. `preparationRef, executionId, executionGeneration, budgetPolicyRef, contextBundleRef, optionsRef`는 원자료에서 재도출해 전부 대조한다. `permissionPolicyRef`는 현재 P2 exact fullref다. 같은 명령 UUID·project·client·control과 같은 payload에 기존 exact `approvalRef:{requestId,decisionId,scopeDigest}`를 넣어 소비한다. 나머지 큐 외피 `targetId=null,expectedVersion=0,baselineRefs=[]`를 유지한다. originReuse가 없는 기존 입력은 기존 null 승인과 형상만 허용한다. 원 등록·준비 명령에는 새 키를 추가하지 않는다. route가 명시 합성 포트로 구성되지 않으면 이 확장도 닫힌다.
4. P2에서 `authorizeExecution`과 `queueExecutionCommand`의 기존 exact EXECUTION ID·세대·소스 범위 규칙을 각각 검산한다. 두 규칙의 기존 `DENY` 우선 및 `REQUIRE_APPROVAL` 거절을 유지한다. 추가로 같은 EXECUTION 범위와 기존 limitPolicyRef 구조를 쓰는 정책 전용 연산 `reuseExecutionStartOrigin`을 제안한다. 이 연산은 외부 명령으로 실행할 수 없고, 기존 AUTO 허용과 유효한 명시 일회 승인 모두를 요구한다. 해당 범위의 유효 `DENY`가 있으면 두 런타임 AUTO 또는 승인 유무와 무관하게 거절한다. 이는 기존 `registerConnector`의 별도 DENY 검사와 합치지 않는다. 이 정책 연산의 허용 목록 추가도 채택 대상이다. P2에 맞는 등록 보호 권한·원 S와 각 원 출처 보호 권한 또한 별도다. `readExecutionStartOrigins`, 승인 요청이나 결정에 별도 승인이 필요한 정책을 이 목적의 승인으로 충족했다고 간주하지 않는다. 권한 정책을 자동으로 작성하거나 바꾸는 절차를 추가하지 않는다.

두 기존 런타임 정책 검사는 `authorizeRuntimePolicy`가 non-null 승인 참조를 422로 거절하므로 새 목적의 승인 소비와 분리한다. 목적·exact 외피·원 S/Q·승인 범위가 보호 검산에 결박된 뒤, 정책 함수 안에서만 사용하는 별도 불변 투영 두 개를 만든다. 투영은 각 operation을 `authorizeExecution`과 `queueExecutionCommand`로 지정하고 `approvalRef:null`로 둔다. project/actor/client/control/실행 ID·세대/소스 범위/한도/P2는 실제 원 명령과 같은 입력이다. 이 투영은 승인 검사를 건너뛰는 공급자나 후속 명령이 아니며, resolver·registrar, 승인 원장, projectReplay, 실제 요청 해시, 영수증·감사·소비에는 exact non-null `approvalRef`를 가진 원 명령만 전달한다. 두 판정의 실패와 더 짧은 기한은 그대로 적용한다.

현재 근거는 `approval-input.ts:12–29,64`, `project-approvals.ts:51–80,113–149`, `runtime-policy.ts:192–214`, `execution-commands.ts:25–52`, `projects/routes.ts:326,330,344–347,378–382`다. 기존 `requestApproval`과 `decideApproval` 핸들러와 기존 보호 조회를 재사용하는 방향이며, 현재 소스가 이 새 목적을 이미 허용한다는 뜻은 아니다.

## 4. 원문 공급의 같은 트랜잭션 경계

`execution-start-context-source.ts:19,32,57–58,71`의 `SyntheticStartContextSource`는 실제 context/준비/정의/환경 메서드를 고정하고, 일반 환경의 `MATCHED`를 요구한다. 원문 공급의 앞·뒤 관측과 fact 재관측을 모두 유지한다. 이 호출선 때문에 §3의 보호 검산을 queue에만 붙여도 정상 소비가 성립하지 않는다.

- 새 목적의 같은 트랜잭션에서만 queue의 실제 승인 검산자가 내부 증명을 생산한다. 증명은 PoolClient 정체성·원 query 함수·txid, 원 actor/client/Session/H/control, 원 명령 ID 및 완전한 요청 hash, S/Q/P1/P2, 승인 요청·결정·scopeDigest, 원 실행/범위와 실제 원문 fullref/최단기한에 결박한다. 보호 검산자가 보관한 private identity로만 조회한다. 호출자가 넘긴 bool·문자열·GUC·raw fact는 증명이 될 수 없다. 다른 명령/트랜잭션이나 만료된 증명은 거절한다.
- 기존 resolver의 합성 fact 소비와 registrar의 `plan → source.describe → register`는 동일 원 명령에 결박된 증명을 소비한다. context/Options 공급은 `#load`의 최초 환경 관측과 최종 환경 재관측에서 §3의 같은 목적 검산을 다시 적용한다. 동일 fullref·head·상태·원문/관계·등록·회수·권한을 재검증하고, 이 목적의 P1/P2 차이만 증명으로 다룬다. 환경 공개 응답과 저장 원자료에는 `MATCHED`를 새로 부여하지 않는다. 기존 `#start`의 fact 체크·identity·writer·expiry와 실제 context/준비/정의/환경·Options canonical bytes/hash/합산 상한을 보존한다. 원 fact/입력에 없는 현재 권위·필드를 생성하지 않는다.
- 소비 중 `inspect/readBody`까지 원문 재조회가 필요하면 exact command/descriptor/manifest/group과 동일 private Tx 증명을 함께 결박하고 기존 lease의 최단기한보다 길게 열지 않는다. `readBody`의 기존 PoolClient 기반 loan만으로 Tx나 명령 일치를 추정하지 않는다. COMMIT/rollback 뒤 증명을 폐기한다. 역사 재조회는 저장 graph만 보호 검산한다. 이 계약은 별도 전달/실행 트랜잭션에 새 원문 권한을 주지 않는다. 증명이 없는 기존 원문 경로는 기존 `MATCHED` 조건을 그대로 요구한다.

## 5. 저장, 원자 소비와 재조회

- 원장 `approval_requests`, `approval_decisions`, `approval_consumptions`와 명령·영수증·감사를 재사용한다. 기존 버전 전이 및 decision/command 단발 유일성을 유지한다. 보관된 요청의 새 한정 JSON 키로 `originReuseEvidence`를 추가하는 안을 우선한다. 값은 exact `{purpose,projectId,originRef,reservationRef,originCommand,subject,execution,p1Ref,p2Ref,stageRequestRef,assignmentRef,roleBindingRef,sessionBindingRef,preparationRef,connectionRef,environmentRef,contextBundleRef,optionsRef,sourceScopes,budgetPolicyRef,dependencies,candidateCommandId,candidatePayloadHash,candidatePayload}`다. `originCommand`는 exact `{serverCommandId,commandId,requestHash}`다. `ExecutionStartOriginStore.read`가 검산한 `serverCommandId`, 원 `request.commandId`, `originHash(request)`로 도출한다. 이 값은 실제 command 행·receipt·audit의 결박 검산을 거친다. `candidatePayload`는 입력의 정규형을 보존하고 `candidatePayloadHash`와 `actionScope.payloadHash`에 모두 일치해야 한다. 나머지는 서버가 검산한 S/Q와 source reader 값이다. `subject`는 S의 정확 HUMAN tuple, `execution`은 S의 정확 ID·세대, `optionsRef`는 원 준비 ref의 기존 START 목적 투영이다. `dependencies`는 명시된 호스트/프로필/Secret 메타데이터/source-root/등록/connector fullref를 `{kind,ref}` 배열로 종류·ID·버전·hash 순서로 담는다. 중복, 미확인 종류, 원문 집합 누락은 거절한다.
- 요청 fullref/contentHash가 위 증빙을 포함한 저장 snapshot을 봉인한다. `scopeDigest`는 기존과 같이 exact actionScope canonical hash로 유지하고, actionScope의 payloadHash와 요청의 candidateCommandId를 exact 명령에 연결한다. 결정은 기존 requestRef와 scopeDigest를 함께 봉인한다. 소비 시 원 snapshot hash와 결정 requestRef까지 맞아야 한다. 요청·결정이 자기 영수증을 선행 증빙으로 사용하지 않는다. 영수증·감사·소비 관계는 서버 명령 ID 발급 후 같은 Tx에서 결박한다. 기존 JSON guard와 원 명령 hash를 재현하기 위해 별도 후보 row가 필요한지 먼저 검산한다. 기존 원장에 목적 한정 저장이 가능하면 새 표를 두지 않는다. 목적 한정 미적용 SQL은 요청/결정/소비 완결을 양방향 검산하고 다른 승인 분기는 기존 함수로 위임한다. 증빙 삭제·부분 저장·임의 operation의 approvalRef 연결을 허용하지 않는다.
- 결정한 명령을 소비할 때 현재 보호 검산과 exact requestHash 대조를 마치고, 같은 project 잠금 아래 기존 `executions(project_id,id)`와 writer 검사를 통과해야 한다. `persistProjectReceipt`의 명령/receipt/audit와 `ProjectApprovals.consume`의 `approval_consumptions` insert 및 APPROVED/v2 → CONSUMED/v3 CAS를 같은 Tx에서 결박한다. 기존 budget reservation, 합성 execution/grant/claim, 큐 command/envelope, START material 및 outbox도 모두 그 Tx에 속한다. 새 독립 `origin consumed` 장부는 추가하지 않는 안이다. S→고정 실행 ID와 기존 execution 유일성·정확 소비/명령 결합이 이 목적의 동시 중복을 막는지 후속 SQL 검수에서 증명한다. 승인 PENDING이 둘 있어도 실행 저장 한 건만 허용한다. 실패한 요청의 권위 소비, budget, queue/material/outbox는 모두 rollback한다. 기존 별도 거절 감사의 제한된 사실은 도메인 쓰기 성공으로 취급하지 않는다.
- `0078_start_execution_material_registration.sql.pending:94,124–132`의 `fn08_start_material_complete`는 승인 소비·payload_ref·영수증 결정·감사 승인 참조가 비어 있다고 전제하며, null 승인과 기존 7키 START 요청으로 원 request hash를 재구성한다. 0082에서 `material_registration_complete`의 START 완결에 목적 전용 분기를 연결하고, 정상 기존 7키/null START는 정확히 기존 0078로 위임한다. 기존 SEND는 0062 경로를 유지한다. 분기는 실제 승인 요청/결정/소비와 원 명령의 결합으로 식별한다. 목적 표식만 있고 증거 일부가 빠지거나, 승인 흔적과 분류가 어긋나면 거절하며 일반 분기로 대체하지 않는다.
- 새 완결은 승인에 봉인한 exact 8키 payload와 `approvalRef:{requestId,decisionId,scopeDigest}`를 포함한 원 START 외피를 재구성해 원 명령 request_hash와 비교한다. `commands.approval_consumption_id`는 정확 소비 ID이고 `payload_ref`는 기존 `ONE_TIME_APPROVAL_SCOPE` 구조의 같은 payload hash와 scopeDigest다. 소비의 명령 ID/decision/정책·scopeDigest, 결정의 요청 ref·동일 P2·APPROVE, 요청의 CONSUMED/v3 및 S/Q 결박을 검산한다. 영수증은 같은 decision ID·HUMAN·P2·원 request hash로 도출한 scope digest, 감사는 실제 exact approvalRef·actor/client/operation/target·같은 receipt digest를 요구한다. `queue/envelope/manifest`의 내부 context·Options 두 ref와 기존 해시는 유지하고 승인 외피나 8번째 키를 envelope/원문에 복제하지 않는다. 합성 START의 기존 grant/예약/writer/outbox/자료 집합과 hash·false 판정은 그대로 검산한다.
- 기존 `material_registration_reverse`의 queue·자료·명령·영수증·감사 역완결과 새 승인 request/decision/consumption 쪽 역완결을 같은 목적에서 양방향으로 연결한다. 원장에는 미소비 PENDING/APPROVED 이력을 허용하지만, CONSUMED에는 정확 START/receipt/audit/queue/material/outbox를 요구한다. 각 방향에서 row 누락·대체·삭제·타 목적 승인 연결을 거절한다. 내부 함수와 deferred 검사의 호출 권한은 목적 한정으로 닫고 기존 trigger/guard를 비활성화하지 않는다.
- 새 저장 bytes는 기존 프로젝트 저장량 분모와 불명/coverage 경계를 따른다. 원 S/Q는 다시 계상하지 않는다. 승인 request/decision/notification/consumption과 추가 증빙의 실제 bytes 귀속, 기존 START rows 및 기존 material 계상의 중복 배제는 `0077`의 등록 준비 승인과 `0078`의 START 기준으로 검수한다. 상한·유료 정책·일반 권한을 확대하지 않는다. 필요한 목적별 비용 투영과 0082 완결 접점의 정확 함수 목록은 구현 지시서 전 확정해야 한다.
- 응답 유실은 미실행으로 추정하지 않는다. 기존 보호 `GET /api/v1/projects/:projectId/approvals/:id`의 목적 한정 분기에서 동일 actor/client와 현재 읽기 권한 아래, stored requestRef·decision·consumption의 exact command ID/hash 및 실제 합성 결과의 영수증/감사를 검산한다. 결과 읽기는 새 START 효과를 만들지 않는다. `CONSUMED` 원 명령과 정확히 대조한 경우에만 보관 결과를 표시한다. 목적 분기의 성공 보조 필드는 exact `originReuseOutcome:{commandId,requestHash,queueCommandRef,status,executionAuthorized,dispatchPerformed}`를 제안한다. 두 표식은 false이며 `status='SYNTHETIC_QUEUE_STORED'`다. `APPROVED`, 권한 회수, 읽기 불능이나 원 명령 불일치는 이전 유실의 미실행을 증명하지 않는다. 원 packet/승인 ref를 보존하고 자동 재명령/승인 재발행을 금지한다. 기존 projectReplay가 fresh 경계보다 먼저 무조건 결과를 돌려주는 방식은 사용하지 않는다. 이 목적에서 역사 조회는 fresh 재사용의 P2·원 수명·재인증을 연장하지 않고, 현재 읽기 허용이 없으면 원문·영수증을 노출하지 않는다. 이 동작은 기존 미구성 프로덕션 경로를 연결하는 허가가 아니다.
