# Anvil v3 위임·결과·검수 양식

상위 계약: [작업계획서](../WORK_PLAN.md). 이 양식은 이번 Anvil 개발의 실행 관리에도 쓰고, 제품이 다른 프로젝트의 문서를 만들 때도 [문서 작성 공통 기준](../design/문서작성_공통기준.md)으로 재사용한다. 예시의 ID·기능명은 프로젝트별 실제 값으로 바꾼다.

## 1. Agent에게 전달할 시작 패킷

아래 항목을 **실제 값으로 채운 뒤** 전달한다. 빈칸·이전 세션의 기억·‘적절히 처리’로 대체하지 않는다. 다른 세션이 접근할 수 있는 공식 프로젝트 경로와 문서를 사용한다.

```text
작업 ID / 개정 / 제목:
왜 하는가 / 사용자에게 생길 결과:
공식 프로젝트 경로 / branch / 기준 HEAD:
설계 경로 / 절 / ID / hash:
작업계획 경로 / 업무 카드 / 개정:
기존 승인 원문·대상/범위 / 후속 수정 지시 / 현재 hash와 변경 영향·미결정:
공통 규칙 / 헌법 / 최신 관련 사용자 지시:
이번 담당 역할 / 책임자 / 결과 검수자:
선행 결과 / 근거 위치 / 이미 끝나 반복하지 않을 부분:
포함 범위 / 하지 않을 일:
읽을 자료 / 실제 입력 데이터·버전:
소비·생산 API/함수·모델·오류·이벤트 계약:
수정 허용 정확 파일 / 공통 파일 소유자:
기존 dirty·untracked 파일별 소유 / 보존할 변경:
작업 환경 / 도구·제품·버전 / 실행기와 실제 대상:
자동 허용 / 실행 전 승인 / 금지 / 유효 범위:
단일 writer 확인 / 실행·쓰기 권한의 유효성:
구현 순서와 체크 가능한 중간 결과:
RED 사례 / 기대 실패와 근거:
GREEN 실제 명령 / 기대 결과 / 핵심 정상·실패 시나리오:
직접 영향 회귀 / 재사용할 기존 증거·불변 조건:
실제 API·DB·브라우저·Agent 중 필수 확인 범위:
QA 자원 이름·소유·수명·정리 / 지속 자료 보호:
완료 조건 / 미실행이면 합격할 수 없는 항목:
제출 파일·증거 / 검수 재현 방법:
오류 횟수·원인 / 다음 미완료 지점 / 중단 시 주의:
rollback 범위 / 데이터 영향 / 승인 경계:
상세 기록·결과 제출 경로:
```

지시 프롬프트는 위 패킷을 중복 복사해 길게 늘리는 대신 ‘업무 ID·패킷 경로/개정·기준·수행 지시’를 지정한다. 예: `UI09의 발급된 시작 패킷과 해당 카드에 따라 이전 화면을 구현하고, 지정한 실제 검증 및 결과 양식으로 제출하라. FN14 또는 승인 규칙을 임의 변경하지 말라.` 실제 값이 없는 이 예문은 실행 승인이 아니다.

## 2. 수행자 중간 기록 — 비상 시 이어갈 수 있게

`docs/04_test_reports/AV3/<업무ID>/STATUS.md`에 착수/주요변경/시험/오류/중단 전 갱신한다.

```text
기록 시각 / 담당 / 패킷 개정:
기준 문서 / branch / 시작·현재 HEAD:
업무 상태 / 정확한 현재 지점:
확인 완료 / 진행 중 / 남은 작업:
수정 파일 / 미커밋·비추적 / 관련 프로세스·자원:
실행한 명령·환경·종료·결과·증거:
오류 fingerprint / 실제 횟수 / 원인 확정 또는 추측:
시도·조치·결과 / 반복하지 않을 시도:
미전송·기록 공백 / 미검증 / 승인 대기:
다음 정확한 행동 / 안전 재개 조건 / 금지 행동:
```

단일 writer가 상위 WORK_STATUS에 요약·링크를 반영한다. 여러 Agent가 같은 집계 파일을 동시에 덮어쓰지 않는다. 보고가 없더라도 제품의 실행기 관측을 회수하는 요구는 FN08에 별도로 있다.

## 3. 결과 제출 — 판정 → 이유 → 조치

```text
판정: COMPLETED | FAILURE_REPORT | INCOMPLETE | BLOCKED | CANCELLED
판단 이유: 완료 조건별 충족/미충족과 증거
수행 조치: 실제로 바꾼 범위와 결과
업무 ID / 설계·계획·패킷 버전·hash:
시작·결과 branch/HEAD / 변경 파일 / diff:
각 명령: cwd·환경·정확 명령·종료·실제 결과·증거 위치
사용자 행동: URL/화면/계정 역할/QA ID/순서/기대 결과
증거 범위: unit / 계약 / API / DB / browser / 실제 Agent / 배포 구분
기능 상태: 핵심동작확인 / 구현·미확인 / 부분 / 미구현
미실행·SKIPPED·BLOCKED / 열린 문제 / 보안·데이터 위험:
정리: 생성 자원·제거/보존 이유·실제 잔류 확인
rollback 방법 / 데이터 손실 영향 / 필요한 승인
상태 파일·WORK_STATUS 갱신 / 다음 지점 / 후속 소비 업무
```

정식 실패는 같은 문제를 식별할 fingerprint, 원인/근거, 변경/검증, 남은 작업과 Main의 구체적 판단 필요사항이 있어야 한다. 도구중단·quota·권한·환경만으로 코드 정식실패 횟수를 증가시키지 않는다. 허가 범위에서 해결 가능한 문제를 사용자에게 떠넘기지 않는다.

## 4. 검수 카드 — 제출과 합격 분리

검수자는 작업 패킷·설계·실제 diff/명령/자료를 비교한다. 독립 read-only 검수 여부·담당은 승인된 실행 방식에 따라 정하며 이 양식 작성만으로 새 Reviewer 세션을 만들지 않는다.

| 번호 | 확인 | 합격 근거 | 불합격 시 |
|---|---|---|---|
| R1 | 목적·설계·최신 지시와 같은 일을 했는가 | 기준 버전·명시된 결과·실제 산출물 | 잘못된 범위는 보완/새 승인 구분 |
| R2 | 선행 계약과 허용 파일·권한을 지켰는가 | 실제 diff·대상·환경·writer | 범위 이탈·데이터위험 우선 처리 |
| R3 | 정상 사용자 흐름이 끝까지 연결됐는가 | 화면→처리→저장/실행→재조회 | UI/API 일부는 부분 구현 |
| R4 | 중요한 실패·권한·중복·비밀을 확인했는가 | 지정 음성 시험·서버 거부·관측 | 미실행은 합격 아님 |
| R5 | 증거가 현재 결과·환경의 것인가 | command·exit·시간·commit·entity | 이전/다른 환경 증거 분리 |
| R6 | UI 상태·원문·버전·이력이 사실과 같은가 | 실제 API/자료·화면 대조 | 원인/완료 허위 표시 보완 |
| R7 | 직접 영향 회귀·정리·복구를 확인했는가 | 영향 범위·잔류/보존·rollback | 무관한 전수시험 추가하지 않음 |
| R8 | 다음 세션이 이어갈 기록이 있는가 | STATUS·미커밋 소유·다음 지점 | 기록 보완 후 인수 |

검수 결과는 `ACCEPTED / REWORK / BLOCKED / NOT_EXECUTED`와 함께 조건별 근거·영향·재작업 범위·재검수 조건을 기록한다. 검수 자체가 미실행이면 ‘자체 시험 확인’과 ‘독립 검수’를 구분한다. 변경하지 않은 동일 증거를 불필요하게 재실행하지 않고 무엇을 재조회·재현했는지 명시한다.

기능 상태의 위 약칭은 `구현 완료·핵심 동작 확인 / 구현했지만 동작 미확인 / 부분 구현 / 미구현`으로 저장/표시한다. 수행자 주장·실행기 직접 관측·검수자 확인/필요 재현의 출처를 따로 적고 실행하지 않은 것을 독립 검증으로 부르지 않는다. 이해 대조는 설계 본문 §6.2의 6항목별 원문/버전·응답·불일치/부족·확인 주체/근거를 결과에 붙인다. 변경한 연결 문서의 드리프트(§4.3.1)와 업무별 계획 §2.2 검수 조건도 패킷/결과에서 누락하지 않는다.

## 5. 인계·재작업·계획 변경

- 재작업은 미충족 조건·근거·수정 허가 파일·추가 검증만 지정한다. 업무 전체를 무조건 처음부터 다시 시키지 않는다.
- 담당 교체는 기존 상태·자료·결정·이유·오류·실행 정리와 다음 지점을 넘긴다. 이해 불일치/정지 불명은 공개한다.
- 범위 변경은 설계/계획 영향·승인·새 패킷 개정을 남긴다. 수정된 업무 ID와 기존 증거의 관계를 보존한다.
- 완료된 업무 수정은 이유·전후 diff·영향 소비 업무·재확인 범위를 기록한다.
