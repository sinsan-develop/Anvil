# F-20/U-01 R48 Critical Alert ACK 개발 결과

## 판정

`COMPLETED` — developer-primary의 exact18 로컬 구현·기본 검증 및 독립 검토 Important1의 harness 보완 범위 완료. WSL-server 격리 PostgreSQL 15/HTTPS 합성 IdP/Chromium 실측과 최종 R48 수락은 Main 검증 전이므로 **미검증**이다. F-20/U-01 전체 미수락, Release `DEFER`, Production 미실행을 유지한다.

## 판단 이유

- 시작 기준: branch `codex/f18-wsl-ops`, HEAD `71a6ba5a805880b96331dfb16b2677a96a9d2541`, local/private 동일·clean. 직전 기준 `bf2da1bb64fcbc3dffdb58e2e1a14ebcdd4dc3bf`의 후손인 통제 checkpoint. G-05 seq2100 PASS는 Main이 시작 전에 확인했다.
- 정본 binding: 계획 SHA-256 `A0AEC467AD0CEA8689697DF075158B9E5A1B82A8F8FED5DE30DB75CC244FEA58`, WorkInstruction `261DC4F85575BABE0FB56400386C8FEF0BFE5BC6F29BBA6ECCAA201AB4191456`, Invocation `6AB4B8C1887EA42B876F0E84B48B742182A509AE7DDD7D6BE12743468829E6F6`. 시작 전 canonical progress/HANDOFF의 epoch64 `ACTIVE` worker/write lease, actor·만료·exact18 scope 및 서로 다른 종속 fencing token을 확인했다. 이 문서에는 token 원문을 싣지 않는다.
- API는 ACK 1개 route와 정확한 `operations:alerts:acknowledge` permission만 추가했다. 기존 인증·Origin·CSRF·precondition·Idempotency-Key 경계 뒤에서 project/environment scope를 먼저 검증한다. 서버가 open Critical의 검출 sequence/evidence hash를 대조하고 principal actor·서버 발급 `ack:<opaque>` receipt를 실제 append-only 감사 Event에 남긴다. 재요청·경합은 409, scope 밖은 403, 범위 내 unknown은 404다. 기존 내부 idempotent `_transition` 소비자는 변경하지 않았다.
- UI는 메모리 CSRF 없이는 ACK를 차단하고 POST 성공 응답만으로 완료를 표시하지 않는다. 기존 scoped audit GET에서 ACK sequence·alert ID·receipt·evidence hash 일치를 확인해야 완료한다. 감사 조회 실패·미도달·불일치는 실패-폐쇄하고 POST를 자동 재전송하지 않는다.
- OIDC는 configured callback redirect를 같은 origin `/`로 바꾸고, 사용자 클릭 popup과 opener에 독립 보관한 browser_state·정확 origin·Window를 대조한다. popup 첫 실행에서 URL의 code/state를 지운 후 opener로 전달한다. state 불일치·popup 종료·중복/직접 진입·토큰 소실은 재인증 경계다. 기존 callback POST body/schema, 서버 PKCE·pending/session 계약과 공유/외부 IdP는 변경하지 않았다.
- 독립 검토 Important1 보완: R48 전용 WSL opt-in harness에 5개 분리 시나리오를 넣었다. 첫 redirect GET의 code/state 유입을 확인하되 현재 URL/history state/DOM/후속 Referer 잔여0과 `no-referrer`·`no-store` 헤더 및 합성 HTTPS 두 listener의 `access_log=False`를 검증한다. 실제 PG role permission을 순차 변경해 ACK 403과 audit GET 403을 확인한다. 같은 인증 세션으로 잘못된 CSRF·Origin 요청의 실제 HTTP 403을 확인한다. audit 페이지 미도달은 Chromium route에서 유효하나 대상 ACK가 없는 합성 audit 응답으로 주입해 UI 미확인·POST 재전송0을 검증한다. 이 마지막 항목은 실제 audit 서버 장애를 재현한 것이 아니라 UI 실패-폐쇄 검증이다. 정상 ACK는 마지막 별도 시나리오에서만 실행한다.
- WSL 첫 실측 실패 1회: Main이 정확 SHA `dfd50362`로 시작한 격리 PG CAS에서 `_isolated_dsn()`이 `postgresql+psycopg://`를 `postgresql://`로 바꾸어 SQLAlchemy가 미설치 psycopg2를 import하며 `ModuleNotFoundError`가 났다. 제품/API 문제가 아닌 테스트 하네스 DSN 변환 결함이다. exact18의 `tests/integration/test_f20_u01_r48_ack_pg15.py`만 수정해 두 opt-in 테스트가 공통으로 쓰는 helper가 검증된 loopback:5545/동일 사용자·DB 대상을 `postgresql+psycopg`으로 정규화하도록 했다. psycopg2 설치·제품 계약 변경은 없다. 새 SHA의 WSL 재실행 전이므로 PG CAS 및 브라우저 PASS 주장은 보류한다.
- DSN delta 독립 검토 Important1: URL query의 `?host=remote.invalid` 또는 `?dbname=other`가 외형상 격리 대상 검사를 통과한 뒤 실제 SQLAlchemy 연결 대상을 바꿀 수 있었다. `_isolated_dsn()`에서 query가 조금이라도 있으면 fail-closed 거부하고 두 우회 입력의 음성 테스트를 추가했다. 수정 전 `DID NOT RAISE` RED, 수정 후 GREEN을 확인했다. WSL 새 SHA 실측은 여전히 미검증이다.
- WSL 두 번째 실측 실패 1회(누적 2회): Main의 정확 SHA `b1ac03c9` 격리 PG CAS에서 `PostgresOperationsRepository(dsn)`이 `psycopg.connect`를 직접 사용하므로 `postgresql+psycopg://`를 libpq가 `missing "="`로 거부했다. 원인은 한 DSN을 SQLAlchemy dialect URL과 libpq URL 양쪽에 전달한 테스트 하네스 결함이다. `_isolated_dsn()`은 검증·query 거절 후 libpq용 bare `postgresql://`를 반환하고, 두 `sa.create_engine` 호출만 `_sqlalchemy_dsn()`으로 psycopg3 dialect URL을 사용한다. `PostgresOperationsRepository` 두 위치와 OIDC host의 `ANVIL_DATABASE_URL`은 bare URL을 사용하며 runtime 설정이 psycopg3으로 정규화한다. 제품/API/의존성 변경 없이 두 소비자 주소의 host=127.0.0.1·port=5545·user=DB·dbname=DB 일치를 `conninfo_to_dict`와 SQLAlchemy `create_connect_args`로 실제 접속 없이 검사했다. query 우회 거절은 유지한다. 새 SHA의 WSL 재실행 전이므로 PG CAS·브라우저 PASS 주장은 보류한다.
- WSL 세 번째 실측 실패 1회(누적 3회): Main의 정확 SHA `bff7daab`에서 PG CAS 제품 append 후 테스트 `finally`가 `operations_audit_events/heads` DELETE를 시도했고, DB의 append-only trigger가 이를 거절하며 원래 assertion 결과를 가렸다. Main의 전용 DB read-only 조회에서는 sequence 1 `DETECTED`, sequence 2 `ACKNOWLEDGED` 정확 1건이 관측됐지만 이는 테스트 PASS 판정이 아니다. 감사 trigger를 해제하거나 기록 삭제를 우회하지 않았다. CAS·browser 두 fixture의 모든 test-level DB 행 삭제를 제거했고, 감사/사용자/role/OIDC fixture 행은 엄격한 isolated tmpfs/AutoRemove 전용 DB 안에만 남겨 Main이 QA 종료 시 전체 컨테이너 폐기로 정리한다. 로컬 listener·engine은 여전히 닫되, 그 정리 실패가 원래 테스트 예외를 가리지 않도록 원래 예외에 정리 오류 종류를 note로 붙인다. 정리 경로의 append-only DELETE 부재와 원래 예외 보존을 단위/정적 음성 테스트에서 RED→GREEN 확인했다. 새 SHA WSL 실측은 미검증이다.
- WSL 네 번째 실측: Main의 정확 SHA `3571699d`에서 격리 PG CAS opt-in 1건은 PASS. 같은 SHA의 Playwright browser opt-in 첫 `redirect` 시나리오는 `R48_BROWSER_REDIRECT_FAILED`로 실패했고, 기존 child stderr가 `stage=BOOTSTRAP code=UNCLASSIFIED name=AssertionError`만 출력해 정확한 assertion은 확인할 수 없었다. 전용 DB read-only 관측은 CAS scope Event 2건 및 browser scope `DETECTED` 1건·ACK 0건이며 browser PASS가 아니다. 실패가 callback/redirect 검증 전후 어느 assertion인지 현재 증거만으로 확정하지 않는다. R48 전용 고정 시나리오·stage와 정적 `R48_...` assertion 코드만 출력하도록 Node sanitizer를 분리하고, Python test assertion도 동일 정적 허용목록의 한 줄만 전달하도록 했다. raw stack·URL·code/state·토큰·값은 출력하지 않는다. sanitizer 음성 self-test는 RED→GREEN을 확인했다. 첫 redirect 제품/하네스 원인 확정과 같은 계약 내 수정은 새 SHA WSL의 안전 코드 관측 후 수행한다. 합성 IdP 외부 공유 proxy/access log와 첫 GET 순간 Network 노출은 여전히 미검증/잔여위험이다.
- WSL 다섯 번째 실측: Main의 정확 SHA `23927533`에서 `R48_SAFE_FAILURE scenario=redirect stage=REDIRECT_REFERER code=R48_REFERER_LEAK name=AssertionError`. 따라서 첫 redirect GET 존재, root `no-referrer`/`no-store` 응답 헤더, `replaceState` 이후 현재 URL/history state/DOM 잔여0은 통과했고, 후속 `/api/health/ready` 요청의 Playwright `request.headers().referer`가 `undefined`가 아니라는 한 점까지만 확정됐다. 해당 값이 빈 문자열, 정리된 root, code/state 포함 또는 기타인지는 기존 단언이 가려 확인되지 않았다. 정상 후속 요청에 `referrerPolicy`를 강제하는 우회는 하지 않았다. `headers()`·`allHeaders()`·`headerValue('referer')` 세 관측을 `ABSENT|CLEAN_ROOT|CODE_OR_STATE|OTHER` 정적 범주로만 출력·비교하고 모두 `ABSENT`일 때만 잔여0으로 인정하도록 브라우저 하네스를 보완했다. 빈 문자열도 실제 Referer 부재로 분류한다. Node/Python sanitizer 음성 RED→GREEN; 원문 Referer·URL·code/state·토큰·stack 출력은 금지한다. 실제 원인이 빈 헤더 표현 차이인지 정책 위반인지는 새 SHA WSL 범주 관측 전 미확정이다.
- WSL 여섯 번째 실측: Main의 정확 SHA `7a659b7ae13ed36a8695d3d2573b0370bf22bfbd` Chromium opt-in 첫 redirect가 Python `subprocess.TimeoutExpired` 90초로 끝났고, stdout/stderr 캡처 때문에 범주를 얻지 못했다. 전용 감사에는 `DETECTED` seq1, ACK0만 관측했다. 소스 비교상 직전 23927533에서 `popup.evaluate(fetch)`·`waitForRequest`·`request.headers()` 이후 즉시 AssertionError까지 진행했고, 이번 SHA에서 새로 삽입된 blocking 호출은 `request.allHeaders()` 및 `request.headerValue('referer')`이다. 이 두 await 중 하나가 지연 원인이라는 것은 **추론**이며 어느 쪽인지 아직 확정하지 않았다. 일반 후속 GET 자체는 유지하고 `referrerPolicy` 강제 없이, 이미 반환된 것으로 관측된 `request.headers()`의 정적 범주만 검사하도록 최소 보정했다. health 응답 대기와 무관하게 정상 `fetch`를 발신하도록 fire-and-forget으로 바꾸고 Playwright의 페이지별 요청 포착을 기다린다. R48 고정 stage를 stdout에 남기고 Python timeout의 partial stdout에서 마지막 허용 stage만 전달해 원래 timeout도 비밀값 없이 진단한다. `ABSENT`만 잔여0 통과로 인정하고 CLEAN_ROOT/CODE_OR_STATE/OTHER는 계속 실패-폐쇄한다. 새 SHA WSL 결과는 미검증이며 기존 23927533의 실제 Referer 범주도 미확정이다.
- WSL 일곱 번째 실측: Main의 정확 SHA `827c01a1`에서 실제 Chromium `redirect` 시나리오는 PASS였으나 같은 opt-in pytest 전체는 `permission-denied` 시나리오의 90초 timeout으로 FAIL. 안전 partial stage는 `ACK`; 격리 감사 `DETECTED` seq1·ACK0이다. 이는 권한 거절 검증 통과가 아니며 전체 R48 browser PASS도 아니다. 소스상 `ACK` 뒤에는 확인 버튼 대기, `normal` 전용 사전 요청, ACK 클릭, POST 응답 대기, 403 확인, UI 실패-폐쇄 대기, context 종료가 있으며 `permission-denied`에서는 사전 요청을 건너뛴다. 기존 stage 하나로는 어느 await인지 확정할 수 없다. `ACK_BUTTON_WAIT`, `ACK_CLICK`, `ACK_RESPONSE_WAIT`, `ACK_DENIAL_CHECK`, `ACK_BLOCKED_UI_WAIT`, `ACK_CONTEXT_CLOSE` 고정 stage를 추가하고 각 주요 Playwright 대기를 10초로 제한했다. 사용자·URL·응답 원문 없이 다음 SHA에서 정확 경계를 좁힌다. 새 SHA WSL 실측은 미검증이다.
- WSL 여덟 번째 실측: Main의 정확 SHA `10596e442320a61d15c965c9934e2c921a8c2476`에서 실제 Chromium `redirect`는 PASS, `permission-denied`는 90초 timeout(stage `ACK_DENIAL_CHECK`), audit `DETECTED` seq1·ACK0, 전체 opt-in FAIL. 소스상 이 stage에 진입하려면 버튼 대기·클릭·POST 응답 이벤트가 완료되어야 한다. 뒤의 동기 `ack.status()===403`가 거짓이면 즉시 AssertionError여야 하므로 `await ack.json()`의 body read가 지연됐다는 것이 강한 추론이다. API 오류 경로는 유한 `JSONResponse`지만 WSL의 실제 본문 완료 여부는 미확정이다. `403` 및 `PERMISSION_DENIED` 코드 단언을 제거하지 않고 body read를 5초 제한·정적 `R48_PERMISSION_BODY_TIMEOUT` 오류로 실패-폐쇄하도록 분리했으며 `ACK_DENIAL_BODY_WAIT`/`ACK_DENIAL_CODE` stage를 추가했다. 단위 self-test는 즉시 코드·미완료 body 양쪽에서 RED→GREEN; raw 본문·토큰·URL은 출력하지 않는다. 새 SHA WSL 재실측 전 본문 완료 및 UI 차단 PASS는 미검증이다.
- WSL 아홉 번째 실측: Main의 정확 SHA `66fb225abb5537206650c67beb9bcdce5827404d`에서 redirect PASS, permission-denied의 403 응답 헤더 후 `ACK_DENIAL_BODY_WAIT/R48_PERMISSION_BODY_TIMEOUT`으로 5초 실패, pytest 1 FAIL/4 deselected.
