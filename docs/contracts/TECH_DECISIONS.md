# P02 기술 선택 — TD-01·TD-02·TD-03 승인·상세 계약

## FN08-CONTRACT-A1 한정 결정 — 2026-10-17

신산님 직접 승인 A-1은 참조 전용 SourceScope/dispatch envelope·receipt와 비권위 수신함 코드·격리 합성시험이다. 기존1GiB spool/2시간 자동 범위 상한 안에서 첫 수신함은 명시 maxBytes≤1GiB·maxEntries≤1024·record≤4096bytes, scope 전체 targets≤200·경로UTF-8≤1024bytes로 유한화한다. 상한을 높이거나 실제 Agent를 실행하는 권한이 아니다. 새로운 의존성/설치/서비스·실제 source/정식DB/ACL/키/계정/CS1504 nativehelper 변경0이다.

## 1. 선택 기준

Anvil은 기존 코딩 Agent를 쓰는 사용자 소유 제어 시스템이다. 서버의 목적·헌법·지시·문서·대화·결정·증거가 정본이며 Agent 계정/세션/종류가 바뀌어도 남는다. 총괄 판단도 교체 가능한 연결이다. 새로운 자체 코딩 엔진이나 특정 공급자 전용 데이터 저장 구조를 만들지 않는다.

Windows 설치형·PC/모바일 웹은 같은 서버 자료와 권한을 사용한다. 로컬·WSL 개발을 먼저 하고 Oracle 정밀 검증은 별도 승인 뒤 진행한다. 기존 보관 코드는 적합성 검토 없이 복원하지 않는다.

## 4. 빠뜨리면 안 되는 안전 조건

- 설치형 renderer는 Node 기능을 끄고 context isolation/sandbox를 사용한다. 외부 링크·탐색과 IPC 발신자·입력은 제한한다. 사용자 문서의 HTML/명령을 실행하지 않는다. [Electron 보안 지침](https://www.electronjs.org/docs/latest/tutorial/security).
- Windows 비밀 보관 후보는 OS 보호 저장소다. Electron safeStorage의 DPAPI는 같은 Windows 사용자 안의 다른 앱까지 격리하는 장치가 아니다. 보호 불가 시 평문 fallback을 허용하지 않는다. 서버 Secret/백업 키의 보호 방식과 혼동하지 않는다. [safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage).
- Windows 프로세스 트리의 종료·소유 관측에는 Job Object 등 OS 수단을 실제 검증해야 한다. Job Object에 포함되지 않거나 이탈한 프로세스까지 중지됐다고 단정하지 않는다. 구현 경로·종속성·이탈 차단은 P02의 후속 실행기 계약에서 결정한다. 확인 불가면 새 writer를 차단한다. [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).
- API schema는 개발자가 제공하는 신뢰 코드다. 사용자 방법론·양식은 제한된 데이터 모델로 검증하며 사용자 JSON Schema/코드를 서버 검증기에 컴파일하지 않는다. [Fastify 검증 지침](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/).
- 제어권·버전·명령 중복 방지는 DB 트랜잭션/유일 제약으로 검증하고 읽기 후 쓰기만으로 보장하지 않는다. [PostgreSQL 격리](https://www.postgresql.org/docs/15/transaction-iso.html).

## 5. 이 결정과 분리할 항목

1. 첫 실제 Agent 후보 Codex App Server와 둘째 Claude CLI/SDK의 공식 계정 사용·비용·중지 계약. 상세 근거는 CAPABILITIES.md. 기술 구성 선택이 특정 공급자 과금·로그인 사용권을 부여하지 않는다.
2. Anvil 사용자 인증·역할·실행기 등록/보호 저장소·서버 Secret 참조. 기존 OIDC/DB/인증서를 자동 재사용하지 않는다.
3. 영속 DB/파일 경로와 schema·공통 port·백업 위치/주기/보존·단절 한도·측정 표본. 제안과 사용자 확정값을 나눠 후속 기록한다.
4. 원격 Git의 신규 기준선과 실제 업로드 payload·P03 개발 환경 생성. 기존 원격/자료를 임의 변경하지 않는다.

## 7. 성능·이전 손실 측정 제안 — 수치 미승인

판정 수치를 지금 정해 합격시키지 않는다. 우선 다음 표본/환경으로 기초값을 측정해 신산님께 목표와 비용을 함께 제시한다. 이 제안은 실제 LLM 호출·실사용 원문 외부 전송 승인이 아니다. 합성/허가된 QA 자료를 사용하고 익명화와 전송 대상을 확인한다.

## 8. 보존·단절 정책 결정 순서

- 백업 대상은 사용자 원본/버전/관계/승인·실행/첨부와 비밀 제외 연결 참조다. 소스/미커밋 포함은 개별 선택하며 Agent 계정·비밀·복호화 키는 자료 묶음과 분리한다.
- 권장 방향은 서버 데이터와 분리된 사용자 지정 백업 위치, 정기 백업+변경 전 checkpoint, 검증 복원이다. 실제 드라이브/네트워크 위치·주기·보관 기간·용량 상한·암호화 키 보관은 아직 결정하지 않았다. 기존 Backup 경로를 새 제품의 자동 저장 위치로 쓰지 않는다.
- 보관 만료 자료를 자동 삭제하는 정책과 백업 생성 정책을 분리한다. 정책 미설정을 무제한 자동 실행/무기한 보존 보장/자동 삭제로 해석하지 않는다. 정책 변경 시 영향과 기존 참조 보호를 보여준다.
- 통신 단절 시 새 단계/새 승인/허가 범위 확대는 금지한다. 진행 중 작업의 계속 가능 시간·spool 용량·보호 기한은 환경별 결정이다. 기록 실패/디스크 부족·소유권/정지 불명 시 안전 차단하고 관측 공백을 공개한다. 사용자 확인 없이 재기동 자동 재개하지 않는다.
- TD-01 뒤 실제 자료 규모·서버 저장 공간과 기초 측정에 근거해 한 번의 정책 검토 묶음으로 제안한다. 수치 없는 현 문서를 설정 완료나 시험 통과로 표시하지 않는다.

## 11. Windows OS 연결의 내부 구현 경로 — 실제 검증 전

P02의 미정 OS binding을 배정 가능한 정확 파일로 좁힌 Main의 기술 상세안이다. TD-01 서버/실행기 Node·웹/Electron 구성을 바꾸지 않고, Node에서 직접 없는 Windows API 경계만 작은 C# helper로 분리한다. 새로운 OS 서비스/driver·관리자 권한·보안 제품/계정은 추가하지 않는다. 다른 역할/기능 범위나 실제 실행 허가가 생긴 것이 아니다.

2026-10-16 읽기 관측에서 Windows 제공 compiler `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`와 x86 대응 파일의 version `4.8.9221.0`을 확인했다. compiler 실행/파일 생성·Agent 호출은0이다. 이 파일 존재는 .NET helper build/호환·패키징 합격이 아니며 P03/해당 FN에서 실제 확인한다. 새 compiler/원격 dependency를 먼저 설치하지 않는다.

범위: `apps/connector/native/OwnershipHost.cs`(고정 입출력 schema·프로세스/Job Object 관측), `apps/connector/native/ProtectedStore.cs`(사용자 범위 OS 보호 저장), `scripts/build-windows-helper.ps1`(정확 compiler·고정 source→등록 산출물), Node bridge `apps/connector/runtime/windows-host.ts`. helper는 임의 shell 코드/파일 경로를 stdin으로 실행하는 엔진이 아니며 검증된 실행 spec/허가 receipt·고정 연산만 받는다. 생성 산출물 위치/hash·실행기 패키지 포함·서명/신뢰는 P03/FN18에 결박한다.

소유 경계는 정확 executable path/인자·cwd를 검증하고, 새 process를 suspended 상태로 만들고 소유 job 배정/설정이 성공한 뒤 resume하는 경로를 우선 검증한다. job 배정 실패·도구 호환/이탈 통제 미확인은 변경 역할 준비 실패이며 우회 launch를 하지 않는다. handle 상속은 필요한 pipe만, PID/생성시각·process handle/host와 실행 세대 결박, breakaway/이탈·잔류·관측 누락을 실제 확인한다. KILL_ON_JOB_CLOSE를 자동 기본값으로 쓰거나 shared process를 강제 회수하지 않는다. [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)의 기능을 사용하는 안이며 전체 OS/파일 격리나 모든 자식 통제를 이미 증명한 것은 아니다.

DPAPI 사용자 범위 보호는 실행기 credential/등록 개인키의 저장 경계로 사용한다. 같은 Windows 사용자·관리자/침해된 앱에 대한 완전 격리를 보장하지 않으며 평문 fallback0, 보호 실패는 등록/새 호출 차단이다. 서버 Secret/backup 키는 Windows DPAPI로 보호한다고 혼동하지 않는다. [CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) 근거와 실제 다른 사용자/복호화 실패·로그 비노출 검수를 분리한다.

등록 host 증명은 실행기 로컬 생성 키의 공개키 fingerprint와 서버 일회 challenge 서명을 결박한다. 서명 안은 ECDSA P-256/SHA256·IEEE-P1363 고정64byte 서명의 base64url, public key는 SPKI DER base64url·fingerprint는 SHA256이다. server/client nonce는 각각 CSPRNG32byte다. Node↔Windows의 정확 서명 형식은 고정 벡터/상호 검증·변조/재사용 거절 시험 전 지원으로 표시하지 않는다. 실제 키 생성은0이다.

서명 대상은 버전1 canonical UTF-8 구조 `{protocolVersion,installationId,registrationId,scopeDigest,publicKeyFingerprint,serverNonce,clientNonce,expiresAt}`의 SHA256이며 그 원문 byte를 Node가 helper에 전달한다. challenge의 ID/범위/기한·public key/사용자 비교 확인·서명·미사용을 함께 검증하고 credential 발급/일회 소비를 원자 저장한다. 이는 OS 원격 attestation이 아니며 계정/기기 소유와 같은 OS 사용자/관리자에 대한 보호 한계를 UI11에 표시한다. 등록 서명이 있다고 이후 모든 Bearer 요청이 하드웨어에 결박된다고 주장하지 않는다. token은 HTTPS/OS 보호·scope·기한·서버 회수 검사로 다룬다.
