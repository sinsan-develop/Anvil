## 1. 발급 전과 사용 전의 증빙

| 시점 | 검산할 근거 | 아직 결정할 경계 |
|---|---|---|
| 발급 전 | 현재 HUMAN/Session/H/제어와 발급 목적 정책, 원 S/Q와 확정 부모 원장, fresh WAITING/head, 실제 보호 출처·등록과 원 논리 Session. 실행 전 독립 관측이 가능한 준비 증빙과 실행 예산 근거를 원 발급 범위에 결박 | 발급을 허용하는 목적과 주체, 준비 증빙의 생산자·서명 목적·수명, 실행 예산의 수요·정책·예약 근거 |
| 생성 뒤 사용 전 | 같은 실행 시도의 실제 Query·init SID·child·writer 중 해당 사용에 필요한 관측, 현재 등록·회수·credential 목적·기한. 관측을 원 귀속·grant/E와 대조 | 사용별 필수 증빙과 실제 관측 생산자, 사용 개시 조건과 회수 검사 지점 |

생성 이후에만 생기는 관측은 최초 발급 전제에 넣지 않는다. 발급 전 필수 근거를 실제로 생산할 수 없으면 효과 전 거절한다. S/Q의 미검증 표시, 환경 선언, 준비 권한과 합성 current로 실제 관측을 대신할 수 없다. 이 분리는 실제 생성 권한을 부여하지 않는다.

실행 예산의 원 정책·명시 수요·참조를 발급 해시보다 앞서 확정할 수 있는 생산선이 필요하다. 선행 계획은 그 계획을 소비할 자기 발급 결과나 영수증 해시에 의존할 수 없다. 사용량 예산과 프로젝트 저장량 예약은 각각의 기존 목적과 계상식을 적용한다. 발급 범위의 정확 해시 입력과 증빙 목적은 채택 단계에서 고정한다.

## 2. 단발 귀속, 전달, 사용과 회수

아래 이름은 검토용 상태다. 공개 DTO나 SQL 열을 확정하지 않는다.

| 경계 | 확인할 사실 | 후속 효과와 재조회 |
|---|---|---|
| 귀속 COMMIT 확인 | 원 origin과 START·Q/E 대응, 원 명령·영수증·감사·비용의 양방향 관계가 정착했다 | 같은 명령은 원 귀속과 보호 조회용 상태를 돌려준다. 귀속만으로 비밀이 전달됐거나 사용 가능하다고 표시하지 않는다. |
| 전달 시도 선점 | 확정 귀속·목적·수신자·기한을 다시 대조하고, 외부 효과 전에 한 번의 전달 시도를 영속적으로 소진한다 | 승인된 보호 채널의 선택된 수신자에게만 자격 자료를 한 번 공급할 수 있다. 시도 소진 후 중단이나 응답 유실이 나도 자동 재전달하지 않는다. |
| 전달 관측 | 채택된 관측 방식에서 같은 시도와 수신자의 결과를 확인했다 | 전송 완료, 수신자 수용, credential 사용 개시는 별도 사실이다. 사용 허용은 채택된 증빙과 후행 사용 검산을 충족한 경우에만 가능하다. |
| 회수 | 원 grant/E에 귀속된 명시 회수가 정착했거나 현재 검사가 더 이상 허용하지 않는다 | 이후 전달·사용을 거절하고, 이미 시작한 작업의 정지와 writer 회수는 각각 실제 증거로 확인한다. 늦은 전달 결과가 회수 상태를 되돌릴 수 없다. |
| 결과 불명 | COMMIT, 전달 또는 상대 수용 결과를 확인하지 못했다 | 불명인 경계를 분리해 원 명령·귀속·시도를 보존한다. 정착하지 않은 원 작업의 점유를 유지하고, 확인된 사실만 새 보호 조회로 회복한다. 새 명령·토큰·START·nonce를 자동 생산하지 않는다. |

COMMIT 결과 불명은 저장 상태가 확인됐다는 뜻이 아니다. 원 귀속의 정착을 확인하기 전에는 전달을 시작할 수 없다. 확정 COMMIT 뒤 전달 전 중단과 전달 시도 소진 뒤 결과 불명은 구분한다. 어떤 복구에서 아직 소진되지 않은 원 시도를 시작할 수 있는지는 별도 결정 사항이다.

한 번 공개할 대상은 선택된 보호 채널에 공급되는 자격 자료다. 명령 영수증·보호 조회에는 원 참조와 검산 가능한 상태만 둔다. raw 비밀은 응답·로그·S/Q·역사 결과에 넣지 않는다. 동일 명령 조회, 새 로그인, timeout, 취소나 늦은 응답으로 재공급할 수 없다. 수신 관측 방식과 비밀 폐기·digest·회수 경계가 채택되기 전까지 실제 전달 권한은 미정이다. 기존 Native 준비 통로의 용도 확장은 이 문서에서 결정하지 않는다.

## 3. 원자 순서와 남은 결정

1. 원 project 잠금과 같은 Tx에서 주체·정책·S/Q·보호 출처를 검사한다. 발급 전 증빙과 실행 예산 참조를 도출하고, 원 ID를 고정한 뒤 자기 영수증을 참조하지 않는 발급 원문을 봉인한다.
2. 같은 Tx에서 저장량을 예약하고 원 귀속·대응·명령/영수증/감사·정산의 역완결을 검사한다. COMMIT 완료와 연결 회수를 확인한다. 보호 응답은 새 인증과 원 결과 대조를 거친다.
3. 보호 전달을 위한 후행 경계에서 원 귀속·현재성·회수·수신자를 대조하고, 한 번의 시도를 먼저 소진한다. 그 정착이 확인된 뒤 외부 전달 효과를 시작한다. DB COMMIT과 외부 전달의 결과는 별개로 검산한다.
4. 전달 및 사용 전 검증은 원 S/Q·Session·정책·등록·증빙·예산의 최단 기한을 따른다. 처리 기한은 단조 시간으로 별도 적용한다. 외부 기다림이 끝났다는 사실로 실제 저장·전달이나 child 종료를 추정하지 않는다.

채택 순서는 발급 전 필수 증빙·예산 근거, 원 origin/START/Q/E의 단발 귀속과 발급 목적, 보호 전달·사용 개시·회수와 불명의 의미다. 동일 Tx 봉인, 저장 표의 배치, 잠금과 단발 검사 구현은 이 의미를 고정한 뒤 판단한다.

I3의 SDK init과 첫 입력 순서는 미검증이다. 입력 없이 init이 가능하다면 init 뒤 별도 HUMAN SEND를 선택하는 순서를 검토할 수 있다. 선행 입력이 필요하다면 실제 init SID 없이 원 논리 Session·grant로 별도 SEND를 저장할 보호 근거가 먼저 필요하다. SDK 지원 여부와 해당 근거를 확인하기 전에는 어느 순서도 채택하지 않는다.

## 4. 원자료 정책과 후속 실행 정책의 결박

기존 origin은 원 등록 시점의 정책 ref를 S에 봉인한다. 반면 START queue는 정확한 실행 ID·세대·sourceScopes·한도 ref에 대한 `authorizeExecution`과 `queueExecutionCommand`를 각각 현재 정책에서 검사한다. 이 규칙을 origin 등록 뒤 추가하면 정책 해시가 달라진다. 현 합성 basis는 START의 정책 ref와 원 S의 정책 ref가 같은 경우만 받으므로, 기존 규칙만 있는 원자료 fixture와 실행 규칙을 가진 ledger fixture를 그대로 이어서는 정상 START를 만들 수 없다. 근거는 `execution-start-origin-fixture.ts` 21행, `execution-command-ledger.test.ts` 19–20행, `execution-start-origin-queue-basis.ts` 130–132·148–151행과 `execution-commands.ts`의 두 runtime 정책 검사다.

| 후보 | 정책과 식별 관계 | 채택 시 달라지는 의미 |
|---|---|---|
| A. 후속 START에서 최신 실행 정책을 별도 결박 | 원 S/Q와 당시 등록 정책의 fullref/hash 및 원 C/A/U/R 관계를 역사 증거로 그대로 검산한다. 후속 START는 원 S의 executionId/세대와 같은 범위에 명시 승인된 최신 실행 정책을 자기 입력·결과에 별도 결박한다. | 원 등록 정책과 후속 실행 정책을 서로 다른 역할로 읽는 새 계약이 필요하다. 기존 START의 `permissionPolicyRef`를 쓰는 방식을 우선 검토하고, 저장 증빙에는 어느 ref가 원 등록 근거이고 어느 ref가 후속 실행 근거인지 구분한다. 새 입력 키나 표를 당연히 추가하지 않는다. |
| B. origin 전에 실행 식별을 승인·선고정 | 서버가 origin 이전에 고정한 실행 ID·최초 세대에 대해 명시 실행 정책을 먼저 구성한다. origin 생산자는 승인된 원 식별을 결박하고, 기존 동일 정책 ref 조건을 유지한다. | 선고정 ID의 소유·범위·수명·단발 사용과 원 origin 연결을 새로 정해야 한다. 이 관계에 필요한 보호 입력과 영속 증빙을 검토한다. 호출자가 임의 ID를 정하거나 일반 등록에 쓰던 식별자를 실행 허가로 사용하지 않는다. |

권장 검토 순서는 A다. origin 등록 당시의 S/Q·정책 지문·원 영수증은 재작성하지 않는다. 최신 실행 정책은 현재 origin 읽기권이나 보호 source 검사를 대신하지 않는다. 같은 HUMAN·Session/H·제어, 원 fresh WAITING/head·보호 출처, 원 executionId/세대·정확 sourceScopes·목적과 한도 ref를 유지한다. 현재의 두 runtime 작업은 각각 실제 정책으로 허용돼야 한다. 적용 기한은 원 S/Q·현재 Session·읽기와 source·두 runtime 규칙·한도의 실제 기한 중 최소다. 기존 명시 정책 생산 경계를 소비하며, 자동 정책 부여·성공 대역·임의 식별·과거 해시 수선으로 연결하지 않는다.

PMO가 결정할 항목은 원 등록 정책과 후속 실행 정책의 분리 허용 여부, 두 정책을 후행 명령·영수증과 저장 증빙에 결박하는 의미, 또는 origin 이전 실행 식별의 명시 승인·소유 방식이다. 각 안의 추가 공개 입력·응답과 영속 유일성은 이 선택 뒤 정확히 비교한다. 합성 queue의 기존 실행 중복 방지와 origin별 영속 소비 증빙은 별도로 판정한다. 이 절은 실제 발급 권위나 기존 합성 basis의 정책 검사 변경을 승인하지 않는다.

최소 검수는 정상 원 S/Q의 지문을 유지한 채 적합한 명시 정책으로 같은 실행의 START를 연결하는 사례, 그리고 다른 실행·세대·sourceScopes·목적, 두 작업 중 하나의 미허용, 읽기·source 회수, H/제어 변경 및 최단기한 만료의 효과 전 거절이다. A에서는 다른 최신 정책을 원 등록 지문에 덮어쓰지 않는지, B에서는 다른 소유자·원본·만료·재사용의 선고정 ID가 거절되는지 각각 확인한다. 정상 합성 저장을 실제 발급·전달이나 실행 권위 검증에 합산하지 않는다.
