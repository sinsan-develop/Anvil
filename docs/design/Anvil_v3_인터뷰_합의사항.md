# Anvil 재설계 인터뷰 합의사항

기록일: 2026-10-15

이 대화에서 신산님이 직접 설명하거나 확인한 요구사항을 보존한다. 설계 초안의 근거이며, 상세 설계·화면 시안 전체의 승인이나 제품 개발 착수 기록은 아니다. 기존 승인본과 역사적 개발·실패 기록은 그대로 보존한다.

## 1 최상위 목적

**프로젝트와 지식은 사용자가 소유하는 Anvil에 남고, LLM·개발 Agent·세션·서비스 계정은 필요할 때 붙여 쓰고 버릴 수 있는 실행 도구다.** 총괄에 쓰는 도구도 예외가 아니다. 도구 폐기는 프로젝트 자료 삭제나 제공업체 계정 삭제를 뜻하지 않는다.

신산님이 정한 핵심 이유는 다음과 같다.

- 개발의 주도권을 특정 Agent가 아니라 사용자의 시스템에 둔다.
- 헌법·지시·지식·문서·대화·결정 이유·진행·결과의 중요한 원본을 Anvil에 둔다.
- 같은 Agent의 새 세션으로 바꿀 때도, 다른 LLM·Agent·계정으로 바꿀 때도 손실과 재설명을 최소화한다.
- 목표는 무손실 보장이 아니다. 현재 반복되는 설계 번복·완료 작업 반복·현재 위치 재조사·기본 방침 미준수·목적 상실을 줄이는 것이다.
- 설명 없는 미수행이나 오류, 계정·토큰 한도 때문에 프로젝트가 특정 도구에 붙잡히지 않아야 한다.

Dashboard, 방법론 편집, 세션 화면, 기록과 학습은 이 목적을 실현하는 수단이다. 화면·테스트 수만으로 핵심이 완성됐다고 판정하지 않는다.

## 2 헌법과 사용자 지시

헌법은 작업 후 참고하는 문서가 아니다. Anvil이 원본과 버전을 관리하며, 각 실행 도구가 작업 전에 적용받는 최상위 기준이다. 사용자 최신 지시도 누적 기록하고 해당 작업에 전달한다. 실제 충돌이 있으면 조항·지시·영향을 명시하며 조용한 무시나 임의 변경으로 처리하지 않는다.

Agent의 읽음 선언만으로 준수를 인정하지 않는다. 목적·기본 방침·결정 이유·현재 작업에 대한 이해와 실제 행동을 대조해야 한다. 외부 도구 내부 제약을 제거하거나 숨겨진 원인을 알아낼 수 있다고 가정하지 않는다. 사유를 확인할 수 없으면 원인 미확인으로 표시하고 인계·교체 가능성을 유지한다.

## 3 방법론과 문서 작성

| ID | 합의한 요구사항 |
|---|---|
| INT-01 | 기존 문서 가져오기와 대화 작성을 함께 지원한다. 절차·작업·필요 문서·완료 조건을 추출한 초안을 사용자가 수정·확정한다. 가져온 문서를 바로 실행하지 않는다. |
| INT-02 | 공통 방법론의 여러 프로젝트 재사용과 프로젝트 전용 방법론을 모두 지원한다. 공통 변경은 기존 프로젝트에 자동 반영하지 않고 사용자가 적용 여부를 결정한다. |
| INT-03 | 방법론은 흐름도를 기본으로 순차·병렬·조건 분기·검토 실패 재작업을 정의한다. 사람의 작성·검토·승인 단계를 Agent 작업과 함께 배치한다. |
| INT-04 | 일반 템플릿은 요구사항 정리 → 설계 → 개발계획 → 구현 → 검토·테스트 → 배포 준비 → 사용자 확인이다. 고정 강제가 아니며 사용자 편집이 가능하다. |
| INT-05 | 요구사항 단계에서는 자료와 인터뷰로 기능·사용 흐름·완료 기준·제외 범위를 정리하고 사용자가 확정한다. |
| INT-06 | 설계에는 상세 클릭형 화면 시안이 반드시 있다. 입력·조작·화면 이동·처리·저장·조회·정상·오류·빈 상태·권한 제한을 정의하고 예시 자료와 실제 구현을 구분한다. |
| INT-07 | 설계 확정 후 작업계획과 테스트계획을 작성한다. 화면 작업과 기능 작업을 구분해 상세하게 세분화하고 연결 작업을 명시한다. 설계 누락을 총괄이 확인하고 사용자가 확정한다. |
| INT-08 | 설계 ID → 작업 → 담당 세션·변경 코드 → 테스트 항목·실제 증거를 양방향 연결한다. 기능 목록과 시안 위치에서 시작 전·개발 중·검토·테스트·보완 필요·완료 상태를 조회한다. |
| INT-09 | 사용자가 단계 목적과 결과를 입력하면 총괄이 문서에 근거해 임무·완료 조건을 구체화하고 사용자가 수정·확정한다. |
| INT-10 | 문서는 직접 편집하거나 총괄에 수정 요청한다. Agent 수정은 전후를 확인한 뒤 반영한다. 저장과 실행 적용은 다르다. |
| INT-11 | 진행 중 설계 변경은 영향 분석 → 사용자 승인 → 계획 수정 → 영향 작업 재개다. 영향 없는 작업은 계속한다. 최초 설계·변경 전후·이유·요청자·승인·버전·계획·코드·검증 이력을 보존하고 과거 버전을 조회한다. |

## 4 책임과 실행

총괄은 Anvil에 축적된 지식과 상태에 근거해 프로젝트를 조율한다. 단계마다 서로 다른 Agent의 책임자 세션을 배정할 수 있다. 책임자는 직접 할지 subagent를 활용할지와 작업 방법을 정하고, 계획을 기록한 뒤 허용 범위에서 실행한다. 총괄은 결과를 판정하고 다음 단계나 재작업을 지시하되 사용자 절차·승인 조건을 임의 변경하지 않는다.

| ID | 합의한 요구사항 |
|---|---|
| INT-12 | 책임자 세션은 단계 완료·재작업까지 유지하는 것이 기본이다. 다만 최신 핵심 정의에 따라 필요 시 즉시 교체·해제할 수 있으며 세션 유지는 필수 의존성이 아니다. |
| INT-13 | 사용자는 총괄·단계책임자와 직접 대화·지시·일시정지·재개한다. 추가 지시와 작업 중단 후 지시는 구분한다. subagent는 책임자 아래 임무·상태·결과를 조회하고 기본 지시는 책임자를 통해 전달한다. |
| INT-14 | 자동 진행은 매 작업 확인을 요구하지 않고 지정 승인 지점에서만 기다린다. 건별 진행은 선택한 단계 전체 수행과 총괄 판정 후 다음 단계 전에 기다린다. |
| INT-15 | 파일 수정·테스트·패키지 설치·commit/push·DB 변경·배포 등을 프로젝트별 자동 허용·실행 전 승인·금지로 정하고 모든 도구·책임자·subagent에 적용한다. |
| INT-16 | 같은 파일에 동시 writer를 두지 않는다. 필요하면 Git 작업 공간을 분리하고 총괄이 배정·통합한다. |
| INT-17 | 결과 제출은 곧 완료가 아니다. 총괄이 실제 파일·명령·테스트와 완료 조건을 대조한다. 구현 결과 제출 → 검토·테스트 → 완료를 구분하고 실패 항목은 보완 필요로 돌린다. |
| INT-18 | 이유 없는 정체·허위 완료·불필요한 중단은 증거로 확인한다. 일반 보고는 작업을 멈추지 않는다. 중단에는 이유·영향·필요 결정·계속 가능한 작업을 포함한다. 독립 작업까지 멈추지 않는다. |
| INT-19 | 재개·재작업·담당 교체와 자동 시도 횟수·시간·비용 한도를 방법론에서 정한다. 정상 장시간 실행과 안전 승인 대기를 방치로 오인하지 않는다. 한도 도달 시 근거와 선택지를 사용자에게 제시한다. 사용자의 직접 교체권은 실패 횟수 조건을 기다리지 않는다. |
| INT-20 | 중지 범위는 현재 세션·해당 단계(subagent 포함)·프로젝트 전체로 선택한다. 중지 요청과 실제 확인을 분리하고 결과·복구 기록을 보존한다. |
| INT-21 | 단계책임자는 상세 작업현황 파일을 착수·주요 변경·검증·오류·중단 시 갱신한다. 기준 버전·완료/진행/남은 작업·변경 파일/Git/프로세스·검증·오류/시도/조치·대기 사유·다음 행동·재개 주의사항을 기록한다. |
| INT-22 | 비상 복구 시 총괄이 기록과 실제 파일·Git·프로세스를 대조한다. 사용자가 재개하면 완료 작업을 반복하지 않고 미완료 지점에서 이어간다. |

최종 완료는 총괄의 설계·계획·증거 대조 → 실제 사용 가능·미완료·미확인 정리 → 사용자 최종 확인 대기 → 사용자 확인 후 완료다. 미완료를 남기고 닫는 경우 정상 완료와 구분한다.

## 5 지식과 인계

| ID | 합의한 요구사항 |
|---|---|
| INT-23 | 대화 원문과 구조화 지식을 함께 축적한다. 결정과 이유·실패/해결·현재 작업·미해결 사항·근거 위치를 지속 정리한다. 매번 긴 대화를 새로 요약하는 데만 의존하지 않는다. |
| INT-24 | 총괄이 지식의 중요성과 재사용 가치를 판단하고 임무에 필요한 문서·과거 실패·주의사항을 선별한다. 사용자도 정정·사용 제외할 수 있다. 출처·판단 근거·적용 범위·변경 이력과 사실/가설을 구분한다. |
| INT-25 | 다른 프로젝트·사용자에 대한 지식 공유는 사람이 결정한다. 방법론·작업 규칙의 개선안도 사용자 승인 후 적용한다. |
| INT-26 | 세션·도구·계정 변경에도 Anvil의 원본 자료와 조회 권한은 유지한다. 서비스 계정과 Anvil의 사용자 권한을 분리한다. 외부 계정의 보관 정책이나 사용 한도를 프로젝트 원본의 수명으로 삼지 않는다. |
| INT-27 | 사용자 직접 이전은 현재 기록 보존 → 인계 내용/미해결/기록 부족 표시 → 대상 선택 → 실제 상태 대조 → 재개다. 인계 이력과 원래 근거를 보존한다. |
| INT-28 | 새 세션은 목표·헌법·확정 결정·현재 상태·다음 작업·불명확 부분을 먼저 제시한다. 총괄 교체는 사용자, 단계책임자 교체는 총괄이 이해 내용을 확인하고 재개한다. |
| INT-29 | 종료된 도구에 마지막 요약을 부탁할 수 있어야만 이전되는 구조는 안 된다. 작업 중 중요한 내용을 Anvil에 회수한다. 기존 실행·쓰기 상태를 정리해 중복 수행을 막고 미확인 상태는 공개한다. |

이전 손실의 수치와 합격 임계값은 아직 정하지 않았다. 다만 필수 사례는 이미 명확하다. 동일 Agent 새 세션과 다른 Agent 이전에서 결정 번복, 완료 작업 반복, 현재 지점 상실, 헌법 미준수, 프로젝트 목적 상실을 확인한다. 손실·재확인·사용자 보완 필요 범위를 숨기지 않는다. 다른 Agent의 내부 세션을 그대로 복제한다고 주장하지 않는다.

## 6 도구 연결과 개발환경

처음에는 로컬 설치 Agent만 논의했으나, 이후 신산님이 설치형·웹서비스형·CLI형을 모두 연결 대상으로 설명했고 기능별 지원 표시를 확인했다. 따라서 형태에 따른 일괄 금지가 아니라 실제 제어 지원에 따라 배정한다. 이는 모든 외부 제품의 지원 검증이 끝났다는 뜻이 아니다.

| ID | 합의한 요구사항 |
|---|---|
| INT-30 | 외부에서 사용하던 기존 Agent 세션을 가져오지 않는다. Anvil에서 새로 시작한 세션과 그 프로젝트의 재개·교체를 관리한다. |
| INT-31 | 연결 시 작업 지시·상태 조회·결과 수집·중단·재개·도구 승인 등의 지원 여부를 표시한다. 화면 열기와 실제 제어를 구분하고 필요한 기능이 없는 도구는 해당 역할에 배정하지 않는다. |
| INT-32 | Agent가 지원하는 모델·실행 옵션·사용 한도를 프로젝트 기본값과 단계별로 정하고 허용 범위 안에서 선택한다. |
| INT-33 | Agent 자체의 파일·명령 승인을 PC·모바일의 같은 요청으로 처리한다. 지원 여부를 검증하며 외부 도구의 안전 절차를 우회하지 않는다. |
| INT-34 | 프로젝트별 개발·테스트·배포 환경을 등록하고 소스 위치·실행 방법·필요 도구·접속 정보 참조·허용 작업을 정한 뒤 단계와 연결한다. 도구 실행 위치와 빌드·테스트 대상 환경은 구분한다. |

## 7 서버와 접속

프로젝트 원본은 Anvil 서버에 보관하고 Windows 실행 프로그램은 로컬 Agent를 수행하며 기록을 회수한다. 설치형 앱·PC 브라우저·모바일은 같은 프로젝트를 조회한다. 초기에는 한 PC에 서버와 실행기를 함께 둘 수 있는 구조지만, 신산님의 현재 환경은 **WSL-server가 Anvil 서버, Windows가 로컬 Agent 실행기**다. 서버 배포나 데이터 이전을 실행한 기록은 아니다.

| ID | 합의한 요구사항 |
|---|---|
| INT-35 | 설치형 Anvil과 브라우저형을 모두 제공한다. 설치형·로컬 연결 프로그램의 첫 지원 OS는 Windows다. |

## 8 사용자와 동시성

프로젝트는 여러 사람이 이어서 맡을 수 있지만 한 시점에 한 사람만 지시·수정·승인·실행한다. 동시 조회는 가능하다. 기본은 비공개이며 지정 참여자에게 조회 또는 작업 인수 권한을 준다. 담당자 인계는 작업 안전 대기 → 상태·미결 사항 정리 → 다음 담당자 확인·수락 → 권한 이전이다.

한 사용자가 여러 프로젝트를 동시에 진행할 수 있다. 전체·프로젝트별 동시 실행 수를 설정하며 초과 작업은 대기열에 둔다. 실행 중과 승인·입력 대기를 구분한다.

## 11 다음 상세 설계와 미확인 범위

첫 상세 시나리오는 **헌법·최신 지시 적용 → 임무 전달 → 실제 수행 확인 → 미수행/오류/원인 미확인 표시 → 사용자 교체 → 기록 대조·인계 → 재개**다. 정상·오류·기록 부족·구도구 중지 미확인·새도구 기능 부족·인계 이해 불일치 화면을 구체화해야 한다.

저장 형식, 이벤트·버전·권한의 세부 계약, 인계 자료의 수집·검색·선별, 도구별 공식 인터페이스와 기능 지원, 암호화·백업 복구, 알림 전달과 지원 범위, 이전 손실 측정 기준은 상세 설계와 실제 검증 대상이다. 합의했다는 이유로 이 항목이 구현되거나 검증됐다고 표시하지 않는다.

기존 클릭형 시안은 초기 개념 검토용이며 이번 합의의 상세 화면을 아직 반영하지 않았다. 상세 설계와 클릭형 시안 검토 후에만 새 작업계획을 작성한다. 인터뷰 기록 단계에서 제품 코드·서버·DB·인증·권한·배포·예약 작업을 변경하지 않는다.

## 12 2026-10-15 작업계획 작성과 개발 방법 표준화 직접 지시

신산님은 작성한 상세 설계를 바탕으로 실제 작업을 관리할 계획 작성을 지시했다. 각 subagent/다른 Agent 세션에 위임할 수 있는 정보와 작업 후 쉽게 검수할 정보를 상세히 넣고, 화면 단위와 기능 단위 업무를 구분한다. 세분화는 무조건 작게 자르는 것이 아니라 구분 가능한 책임·결과·검수 단위라는 뜻이다. 이 지시는 계획 작성을 허용하며 제품 구현 착수와 같지 않다.

지금 정한 설계서·작업계획서 작성 방식은 향후 Anvil이 해당 문서 작성을 지시할 때 동일하게 사용한다. Anvil은 우리가 앞으로 SW를 개발하는 방법을 표준화·시스템화하는 제품이며, Anvil을 만들며 실제 사용하는 방법들이 그 원형이다. 이 대화의 대부분도 나중에 Anvil에서 사용할 방법을 정리하는 과정이다.

따라서 문서 작성뿐 아니라 위임·수행·검수·변경·오류·기록·인계 방법을 원문과 근거·버전·프로젝트 적용·실제 결과로 연결한다. Anvil 고유 기능명/ID는 다른 프로젝트에 강제로 복사하지 않는다. 합의와 제안·시행착오를 구분하고 개선·공유·적용의 사용자 결정권을 유지한다.

## 13 기본 내장 방법론과 사용자 정의

신산님은 방법론 몇 개를 시스템에 기본 내장하도록 지시했다. 사용자는 시스템이 정의한 표준 방법론을 선택해 개발할 수도 있고 사용자 직접 정의로 진행할 수도 있어야 한다. 내장 종류/개별 절차의 최종 목록은 아직 확정하지 않았다. 단계형 표준 개발·반복/증분 개발·기존 SW 개선/오류 수정 3종은 상세 설계 제안이며 사용자 확정 목록으로 쓰지 않는다.

후속 직접 결정: 기본 제공 목록은 **구조적 방법론·객체지향 방법론·애자일 방법론** 3종으로 정한다. 직전 담당자의 3종 분류 제안은 대체되며, 각 종류의 상세 단계·산출물 양식·검수 기준은 아직 최종 확정 전이다. 기본 선택/복사 수정/사용자 직접 정의의 경로는 유지한다.

## 14 공식 산출물 양식·LLM 작성·시스템 조회

2026-10-15 신산님 직접 요구: ‘방법론이 공식적인 산출물 양식도 정의를 해야 하고 그 양식대로 LLM이 작성을 해야 하고, 시스템에서 조회 할 수 있어야 해’. 예시로 요구사항정의서, 설계서, 화면시안, 작업계획서, 테스트계획서, 테스트 결과서, 작업진행상황을 명시했다.

양식의 이름/목차만 나열하는 것이 아니라 필수 항목·작성 규칙·검수 기준·적용 버전을 정의하고 단계의 작성 임무에 전달한다. Anvil에서 실제 산출물 본문·렌더 자료·근거·연결·검토/승인·변경 이력을 조회한다. 방법론/공식 양식과 각 프로젝트에서 작성된 결과는 구분한다. 상세 양식 초안과 시안은 검토 자료이며 실제 LLM 작성·영속 저장·제품 기능 완료를 의미하지 않는다.
