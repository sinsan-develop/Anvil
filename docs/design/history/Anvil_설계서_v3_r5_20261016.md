## 1. 제품의 목적과 범위

### 1.1 가장 중요한 정의

**개발의 주도권과 프로젝트 지식은 사용자 소유의 Anvil에 둔다. LLM·코딩 Agent·세션·서비스 계정은 필요할 때 연결하고, 사용이 끝나거나 문제가 생기면 교체·해제하는 도구다. 총괄에 사용하는 도구도 예외가 아니다.**

Anvil이 하려는 일은 두 가지다.

1. 사용자가 개발 방법론을 정의한다. 절차, 설계서, 개발계획서, 테스트계획서, 환경, 헌법, 승인 조건을 함께 정의하는 공간이다.
2. 그 정의에 따라 **기존 코딩 Agent에게 실제 일을 시킨다.** 결과와 근거를 회수하고 다음 단계·재작업·사람의 결정을 연결한다.

목표는 자체 코딩 Agent 개발이나 Dashboard 모니터링이 아니다. 프로젝트가 특정 도구·대화·계정에 갇히지 않도록 만드는 **사용자 소유 개발 제어 시스템**이다.

### 1.2 해결해야 할 실제 문제

| 사용자가 겪은 문제 | Anvil의 대응 | 성공을 확인할 행동 |
|---|---|---|
| 새 세션이 프로젝트의 ‘왜’를 모름 | 목적·헌법·핵심 결정 이유를 독립 원본으로 보관하고 착수 시 전달 | 새 세션이 목적과 이번 작업 이유를 설명하고 그에 맞는 작업을 함 |
| 기본 방침 무시·설계 임의 변경 | 버전 고정 기준 전달, 실행 전 권한 검사, 실제 결과와 설계 대조 | 승인 없는 범위 변경을 완료로 인정하지 않음 |
| 이유 없는 미수행·거부·오류 | 요청/수신/실행/증거를 분리하고 사유 불명은 원인 미확인 표시 | 사용자가 확인된 지점과 다음 선택을 알 수 있음 |
| 세션·계정·한도에 묶여 인계 불가 | 작업 중 원문·판단·진행·산출물을 회수 | 기존 도구가 응답하지 않아도 새 도구에서 미완료 지점을 이어감 |
| 완료 작업 반복·결정 번복 | 완료 근거·결정 이력·현재 위치를 인계하고 이해 대조 | 이미 확인한 작업을 이유 없이 반복하지 않음 |
| Agent의 완료 선언만 있음 | 제출과 검토·검증·사용자 확인을 분리 | 실제 사용 가능한 기능과 미완료를 구분 |

최소 손실 이전이 목표다. 내부 추론·비공개 상태를 완전히 복제하거나 무손실 이전을 보장하지 않는다. 남은 손실과 사용자 보완 필요를 숨기지 않는다.

### 1.3 포함·제외 범위

포함: 공통/프로젝트 방법론, 상세 문서·화면·추적, 총괄과 단계책임자, 실제 Agent 연결, 자동/건별 실행, 승인·중지·회수, 지속 기록, 지식·헌법, 세션/도구 이전, Windows 실행기, 설치형·브라우저·모바일 조회/지시, 사용자 인계, 백업/복구.

제외: 새 코딩 모델·코딩 엔진 개발, 외부에서 시작한 기존 Agent 세션 가져오기, 모든 제품의 지원 보장, Agent의 내부 안전 제한 우회, 토큰 무제한 제공, 임의 인터넷 공개·VPN 구축, 무승인 배포, 실측 없는 완료 처리. 도구 해제는 프로젝트·대화·코드·외부 계정 삭제가 아니다.

### 1.4 우리가 사용하는 개발 방법을 표준화·시스템화한다

신산님의 추가 정의: **Anvil은 앞으로 우리가 SW를 개발하는 방법을 표준화하고 시스템화하는 제품이다. Anvil을 만들 때 실제로 사용하고 정립한 방법들이 그 표준의 원형이다.** 이 대화의 대부분도 향후 Anvil에서 사용할 방법을 정리하는 과정이다.

따라서 제품 개발과 사용 방법 설계가 분리되지 않는다. 목적/헌법을 확인하고, 요구사항을 인터뷰하고, 상세 화면을 설계하고, 구분 가능한 업무로 계획하고, 기존 Agent에게 위임하고, 실제 증거로 검수하고, 변경·오류·인계를 기록하는 방법을 이번 개발에도 적용한다. 이를 재사용 가능한 방법론·문서 양식·실행/검수 규칙으로 Anvil이 관리·수행하게 한다.

공통 문서 작성 기준은 [문서작성_공통기준.md](문서작성_공통기준.md)다. 상세 설계, 위임 가능한 작업계획, 화면/기능/연결 업무 구분, 완료 조건·검수·기록 형식을 다른 프로젝트에도 동일하게 적용하되 프로젝트별 내용을 채운다. 이것은 이번 Anvil 기능명이나 화면 구성을 모든 프로젝트에 강제하라는 의미가 아니다.

대화 원문→합의한 방법과 이유→버전 있는 표준/양식→프로젝트 적용본→작성/실행 임무→실제 결과/검수→개선 제안으로 연결한다. 이미 합의된 방법은 기준으로 보존하고 제안·가설·시행착오는 구분한다. 개선·공유·기존 프로젝트 적용은 사용자 결정 경계를 유지한다. 단순히 대화를 저장하거나 문서 템플릿을 제공하는 것만으로 시스템화가 완료되지는 않는다.

구현 연결: AV3-F01/F02는 방법론, F03은 공통 문서 양식, F04/F05는 계획/추적/변경, F06/F11은 기준과 근거, F07~F10은 위임·진행·검수·기록, F12는 교체/인계를 담당한다. 작업계획의 FN03/FN04/FN05/FN09와 IX01은 공통 기준으로 다른 프로젝트 문서를 작성하는 실제 흐름까지 확인한다. 자동 규칙 승격·무승인 실행 권한 확대는 포함하지 않는다.

## 2. 사용자·책임·시스템 경계

### 2.1 역할

| 역할 | 책임 | 할 수 없는 일 |
|---|---|---|
| 프로젝트 소유자/현재 작업 사용자 | 목적·헌법·요구사항·방법론·설계·변경·권한·최종 완료 결정 | 다른 사용자 권한을 소유자 허가 없이 확대 |
| 조회 참여자 | 허가한 프로젝트·문서·진행·결과 조회 | 작업 지시·편집·승인·재개 |
| 작업 인수 가능 참여자 | 조회하고 인수를 요청, 수락 후 단독 작업 | 인수 전에 현재 담당자와 동시 제어 |
| 총괄 역할 | 단계 배정, 지식 선별, 결과 판정, 영향 분석, 복구·인계 조율 | 사용자 승인 규칙·범위를 임의 변경 |
| 단계책임자 | 임무 수행 방법 결정, 직접 작업/하위 Agent 활용, 결과·상태 기록 | 위임받지 않은 권한을 하위 Agent에 부여 |
| 하위 Agent | 책임자에게 받은 제한 임무 수행·보고 | 독자 범위 확장·프로젝트 전체 지휘 |

총괄은 ‘프로젝트에 지속되는 책임·상태’와 ‘이번에 판단을 수행하는 LLM/Agent 세션’을 구분한다. 총괄 도구를 교체해도 프로젝트의 목적·판단 이력·절차 위치는 없어지지 않는다.

### 2.2 배치와 소유권

```text
Windows 설치형 / PC 브라우저 / 모바일 웹
               │ 같은 Anvil 사용자·프로젝트·승인 요청
               ▼
Anvil 서버 (신산님 현재 배치: WSL-server)
 ├─ 목적·헌법·문서·원문 대화·지식·판단 이유의 원본
 ├─ 방법론·계획·단계 상태·승인·실행 권한·감사 기록
 └─ 실제 결과·증거·체크포인트·인계 자료·백업
               │ 허가된 작업·버전 / 관측·기록 회수
               ▼
Windows 로컬 실행기
 ├─ 연결 기능 확인·권한 경계·진행 중 로컬 복구 기록
 └─ 기존 코딩 Agent 연결 (설치형/CLI/지원되는 웹서비스)
               │
        허가된 소스·빌드·테스트 대상 환경
```

총괄 판단용 도구도 연결 계층을 통해 사용한다. 단순 모델 API를 호출한 경우는 ‘판단 모델 연결’로 표시하고, 기존 코딩 Agent를 실제 실행한 것처럼 표시하지 않는다. 서버·실행기 분리는 책임 경계이며 별도 마이크로서비스 다수를 요구하는 설계가 아니다.

Anvil 사용자 인증과 외부 Agent 계정은 분리한다. Agent 계정 인증 만료·교체는 해당 실행 연결에만 영향을 준다. Anvil 자료 조회 권한은 바뀌지 않는다. 서버 저장소·백업은 사용자가 소유·반출할 수 있어야 한다.

## 3. 전체 사용자 흐름

### 3.1 처음부터 새 프로젝트를 진행하는 흐름

1. 프로젝트 목록에서 새 프로젝트를 만든다. 이름·왜 만드는지·원하는 결과·소스 위치를 입력한다.
2. 공통 방법론 복사 또는 프로젝트 전용 방법론 작성. 문서 가져오기와 대화 보완을 함께 사용한다.
3. 사용자와 총괄이 요구사항을 정리한다. 기능·사용 흐름·완료 기준·제외 범위를 사용자가 확정한다.
4. 상세 설계와 화면을 검토한다. 입력·행동·저장·결과·오류와 화면 이동을 확인한다.
5. **설계 확정 후** 화면 작업/기능 작업/연결 작업으로 나눈 작업계획과 테스트계획을 만든다.
6. 도구·환경·권한·단계책임자·모드를 지정하고 시작 준비를 확인한다.
7. 사용자 시작 지시 → 헌법/최신 지시/기준 버전 확인 → 책임자 이해 대조 → 작업 수행.
8. 실제 변경·시험·기록을 회수 → 총괄 판정 → 보완 또는 다음 단계. 지정 승인 지점에서는 기다린다.
9. 설계·계획·실제 기능·미검증을 대조한 뒤 사용자 최종 확인을 받는다.

프로젝트 생성만으로 실행하지 않는다. 방법론 저장, 문서 확정, 작업 시작은 각각 별도 행동이다.

### 3.2 기존 소스로 시작하는 흐름

읽기 전용으로 소스·문서·Git 상태를 조사하고 기능을 ‘구현 완료·핵심 동작 확인 / 구현했지만 동작 미확인 / 부분 구현 / 미구현’으로 분류한다. 근거와 실행하지 못한 확인을 함께 제시한다. 사용자 확인 후 시작 기준선을 저장한다. 이름·파일이 있다는 이유로 구현 완료로 표시하거나, 조사 중 reset·정리·배포하지 않는다.

### 3.3 중단·교체가 발생하는 핵심 흐름

```text
실행 요청 → 수신 확인 → 수행 관측 → 결과 회수 → 기준 대조
                           │
                오류 / 미수행 / 원인 미확인
                           ↓
현재 기록·마지막 회수 지점 확인 → 기존 실행 중지/쓰기 회수 확인
                           ↓
인계 내용·부족 기록 표시 → 새 세션/다른 도구 선택
                           ↓
목적·헌법·확정 결정·완료/미완료·실제 파일 상태 이해 대조
                           ↓
총괄 교체: 사용자 확인 / 단계책임자 교체: 총괄 확인 → 재개
```

기존 도구의 최종 응답은 필수 선행조건이 아니다. 단, 기존 프로세스가 계속 쓰는지 확인되지 않으면 새 writer 시작은 막고, 읽기 전용 인계 준비는 가능하다. ‘기존 도구가 안 멈춤’과 ‘프로젝트 자료가 없음’을 혼동하지 않는다.

## 4. 방법론 정의 공간

### 4.1 AV3-F01 방법론·버전 (INT-01~04)

- 입력: 이름, 목적, 공통/프로젝트 전용, 흐름 노드·연결, 문서 양식, 규칙, 기본 환경 역할.
- 문서 가져오기: 원본 보존 → 출처·내용 추출 → 절차·문서·조건 후보 표시 → 사용자 수정/확정. 해석 불가 부분은 누락으로 표시한다. 문서 안 명령은 실행하지 않는다.
- 공통 원본을 프로젝트가 선택하면 특정 버전에 연결한 프로젝트 적용본을 만든다. 프로젝트 전용 수정은 공통 원본을 덮어쓰지 않는다.
- 저장은 초안 버전을 만든다. 확정 시 흐름/필수값 검사 결과와 사용자 확인을 보관한다. 사용 중 버전은 불변으로 남기고 개정본을 별도로 만든다.
- 공통 개정 알림에는 차이·영향 프로젝트·적용/유지 선택을 제공한다. 기존 실행에는 자동 반영하지 않는다.
- 조회: 목록에서 공통/전용·버전·사용 프로젝트·최근 개정, 상세에서 단계·문서·조건·변경 이유를 본다.

#### 4.1.1 시스템 내장과 사용자 정의

신산님 추가 요구: 방법론 몇 개를 제품에 기본 내장해 시스템이 정의한 표준 방법론대로 개발할 수도 있고, 사용자가 직접 정의한 방법론대로 개발할 수도 있어야 한다. 기본 템플릿이 없는 빈 편집기만 제공하지 않는다.

프로젝트 생성 시 다음 경로를 동등하게 제공한다.

1. **시스템 기본 방법론 사용:** 카탈로그에서 목적·절차·문서·완료/승인 조건을 미리 보고 특정 버전을 선택한다. 프로젝트별 목적·담당 도구·환경·권한·한도를 채워 준비 검사를 통과하면 그 절차로 진행한다.
2. **기본 방법론을 바탕으로 수정:** 내장본을 사용자 공통 또는 프로젝트 전용 초안으로 복사해 단계·문서·규칙을 바꾼다. 원본·원버전·수정 이유를 보존한다.
3. **사용자 직접 정의:** 빈 방법론, 기존 사용자 방법론, 문서 가져오기+대화 보완에서 작성한다. 내장본과 같은 검증·버전·실행 계약을 적용한다.

카탈로그에는 시스템 제공/사용자 공통/프로젝트 전용을 명확히 구분한다. 시스템 원본은 직접 덮어쓰지 않고 개정·복사한다. 제품 업데이트로 내장 v2가 추가돼도 진행 중 프로젝트의 v1을 자동 교체하지 않는다. 적용은 차이·영향 확인과 사용자 결정 후 프로젝트 개정으로 처리한다. 어떤 방법론을 골라도 권한·보안·데이터 보호 경계를 우회할 수 없다.

#### 4.1.2 최초 기본 내장 3종 — 종류 확정·상세 내용 검토 대상

신산님이 **구조적 방법론·객체지향 방법론·애자일 방법론**을 기본 제공 목록으로 확정했다. 이전의 단계형/반복·증분/기존 SW 개선 분류 제안은 이 목록으로 대체한다. 아래 적용 관점과 문서·검수 구성은 상세 설계 제안이며, 이름 확정만으로 각 방법론의 구현이나 특정 외부 표준의 완전한 준수를 주장하지 않는다.

| 확정 ID·이름 | 적용 관점·상세 흐름 제안 | 문서·검수 구성 제안 |
|---|---|---|
| SYS-M01 구조적 방법론 | 기능·처리·데이터 흐름을 중심으로 분석→구조적 설계→계획→구현·검증 | 요구사항, 기능 분해·처리/데이터 흐름, 데이터 정의, 상세 화면, 화면/기능/연결 작업, 검증 근거의 연결. 구체 표기법·필수 문서는 상세 검토 후 확정 |
| SYS-M02 객체지향 방법론 | 사용자 시나리오와 객체의 책임·협력을 중심으로 분석→객체 설계→계획→구현·검증 | 사용 시나리오, 객체·책임·관계·상호작용, 상세 화면, 작업·시험의 연결. 특정 언어·패턴이나 모든 다이어그램 작성을 강제하지 않음 |
| SYS-M03 애자일 방법론 | 목표·요구 우선순위→이번 반복 범위→필요한 상세 설계/화면·계획→구현·검증→사용자 검토→다음 반복 | 우선순위 요구 목록, 반복 목표/선택 업무, 상세 설계·화면/기능/연결 작업, 완료 기준·검증·사용자 피드백. 반복 완료와 제품 전체 완료 구분. Scrum 등 특정 운영 방식은 자동 확정하지 않음 |

각 내장본은 흐름 그림뿐 아니라 노드별 목적·사람/Agent 역할·입력 문서·작성 공통 기준·임무·산출물·완료 조건·승인 지점·재작업 경로와 자동/건별 설정 항목을 함께 가진다. 사용자 도구 계정·비밀·실제 환경·무제한 권한을 내장하지 않는다. 필요한 프로젝트 설정이 비어 있으면 준비 필요를 표시한다.

#### 4.1.3 상세 화면·검증 연결

S02 방법론 선택에서 시스템 제공/내 방법론/직접 만들기와 복사·수정 경로를 표시한다. S03은 출처·원버전·적용본, 절차/문서/승인 조건 미리보기, 복사 편집과 버전 차이를 제공한다. 현행 정적 SVG의 선택 영역은 이 구분을 아직 상세 반영하지 않았으며 P01에서 개정·검토한다.

작업계획 FN02가 카탈로그·내장 정의·복사/적용/업데이트 비강제를, FN03이 문서 양식 연결을, UI02/UI03이 선택/미리보기/편집을 담당한다. IX01은 기본본으로 시작·기본본 수정·사용자 직접 작성의 세 경로를 저장/재조회/적용까지 확인한다. FN10/IX03은 선택한 방법론의 실제 실행과 승인/보완 경계를 확인한다. 종류를 새로 늘릴 때마다 동일한 노드·문서·검증 계약을 충족해야 한다.

### 4.2 AV3-F02 절차 노드와 연결 (INT-03, 09, 14, 19)

| 노드 속성 | 정의·검증 |
|---|---|
| 고유 ID·이름·목적 | 이름 변경에도 ID 유지. 왜 필요한 단계인지 작성 |
| 수행 주체 | 사람 / Agent. Agent면 총괄 또는 단계책임자 역할 |
| 입력 | 필요한 문서 종류·버전/확정 여부, 선행 결과, 환경 |
| 임무·범위 | 할 일, 하지 말 일, 변경 가능한 대상, 결과물 |
| 완료 조건 | 실제 확인 방법·증거·판정자, 제출만으로 충족되지 않음 |
| 승인 지점 | 시작 전/완료 후 사용자 승인 여부와 정확한 대상 |
| 진행 모드 | 자동 범위 또는 건별. 기본값과 프로젝트 재정의 구분 |
| 보완 경로 | 어느 조건이 실패하면 어느 노드로 돌아가는지 |
| 한도 | 자동 시도·시간·비용·동시 수행 수. 미설정은 자동 재시도 금지로 제안 |
| 상태 기록 | 책임자 기록 위치·필수 기록 시점·증거 요구 |

연결은 순차, 병렬 분기, 조건 분기, 합류, 재작업을 구분한다. 분기 조건은 구조화 결과/사람 판정으로 평가하며 근거를 저장한다. 자유문장만 있어 기계 평가할 수 없으면 총괄 판단 단계로 표시한다. 합류는 ‘모두 완료/지정 조건 충족’을 명시하고 생략된 분기를 완료로 위장하지 않는다. 의도한 재작업 연결 외 순환, 연결되지 않은 노드, 도달 불가 완료점, 조건 공백은 확정을 막는다.

### 4.3 AV3-F03 문서 양식·요구사항 (INT-05~07, 10)

양식은 문서 종류·필수 항목·예시·검토자·확정자·연결할 노드를 가진다. 이름이나 목차를 프로젝트마다 바꿀 수 있지만 필수 연결의 누락은 검사한다.

| 문서 | 필수 내용 |
|---|---|
| 요구사항 | 사용자·문제·목적, 기능 목록, 실제 사용 흐름, 완료·제외 범위 |
| 상세 설계 | 항목 ID, 처리·저장·조회, 상세 화면/상태, 권한·예외·연동, 검증 기준 |
| 개발계획 | 설계 ID와 화면/기능/연결 작업, 책임·의존·범위·완료 조건 |
| 테스트계획 | 설계·작업 ID별 정상/중요 실패/권한·데이터 위험, 환경·증거·미실행 처리 |
| 환경 정의 | 소스·실행 위치·대상 환경, 도구·명령, 비밀 참조, 허용·금지 대상 |
| 작업현황·결과 | 실제 수행/미수행, 파일·명령·결과·문제·다음 행동·안전 재개 |

직접 편집은 임시 저장→검토→확정이다. Agent 수정 요청은 별도 변경 제안을 만들고 전후 diff·근거·영향을 보여준다. 적용하지 않은 Agent 제안으로 기준 문서가 바뀌지 않는다. 동시 편집의 기준 버전이 다르면 덮어쓰지 않고 충돌 비교를 연다.

## 5. 설계·계획·개발의 연결

### 5.1 AV3-F04 추적 구조 (INT-07~08)

```text
요구사항 R → 설계 항목 D ─→ 화면 S의 특정 위치/동작
                   └────→ 계획 T (화면 / 기능 / 연결)
                             ↓ 책임 단계·세션·실행
                           변경 파일·diff·commit
                             ↓
                           테스트 TC·실제 증거 E
                             ↓
                           항목 판정·사용자 확인
```

설계 항목에는 ID, 제목, 이유, 요구사항 출처, 현재 버전, 화면 위치, 처리/데이터/권한, 완료 조건을 둔다. 계획 작업에는 ID, 설계 버전, 유형, 담당 단계, 입력/출력, 의존, 변경 범위, 시험을 둔다. 한 설계가 여러 작업으로 나뉘고 여러 작업이 한 화면을 완성할 수 있다. 역방향으로 코드/시험을 눌러 왜 만든 것인지 조회한다.

화면과 API·DB 일부만 있으면 ‘부분 구현’이다. 계획에 화면 작업과 기능 작업이 각각 끝났어도 실제 연결 확인이 없으면 해당 기능의 핵심 동작 확인은 아니다. 완료 배지를 수동으로 누르는 것만으로 증거를 만들지 않는다.

| 표시 축 | 값 | 의미 |
|---|---|---|
| 작업 진행 | 시작 전 / 개발 중 / 검토 / 테스트 / 보완 필요 / 완료 | 어느 단계 어느 지점인지 |
| 기능 사용 가능성 | 미구현 / 부분 구현 / 구현·미확인 / 구현·핵심 동작 확인 | 실제 기능의 존재·사용 가능 여부 |
| 검증 범위 | 확인 / 실패 / 미실행 / 차단 / 해당 없음 | 무엇을 어느 환경에서 확인했는지 |

서로 다른 축을 한 초록색 배지로 합치지 않는다. 시안의 상태 오버레이를 누르면 연결 작업·증거·미완료 이유로 이동한다. 시안만 있는 현재 문서는 모든 제품 구현 여부가 미확인인 설계 산출물이다.

### 5.2 AV3-F05 설계 변경·역사 (INT-11)

1. 직접 수정 또는 대화에서 변경 요청 생성. 요청자·시각·이유·전후를 보존한다.
2. 총괄이 영향 설계·화면·계획·진행/완료 작업·테스트·승인을 추출한다. 자동 연결 없는 부분은 ‘영향 미확인’으로 남긴다.
3. 범위·요구사항·위험 변경과 단순 문구 수정의 차이를 보여준다. 설계 변경은 사용자에게 적용 승인을 받는다.
4. 승인한 새 기준으로 계획을 개정한다. 기존 결과는 삭제하지 않고 ‘이전 기준 결과/재확인 필요’로 표시한다.
5. 영향을 받는 작업만 재준비·재개한다. 무관한 작업은 계속한다. 승인·계획 개정 전 영향 작업에는 새 기준을 쓰지 않는다.

각 설계 ID의 이력에서 원안→변경 이유→승인→계획 개정→코드→검증→판정을 시간순 조회한다. 과거 버전은 읽기 전용이며 복원은 새 개정 생성이다. 과거 이력 삭제나 이미 발급한 승인의 소급 변경은 아니다.

## 6. 헌법과 지시의 실제 적용

### 6.1 AV3-F06 기준 관리

헌법은 프로젝트 목적·반드시 지킬 원칙·금지 범위·승인 규칙의 버전 있는 원본이다. 긴 대화의 마지막 요약에 묻지 않는다. 사용자 지시는 원문·발신자·대상·시각·유효 범위·대체한 지시와 함께 저장한다. 우선순위는 사용자에게 보이고, 서로 충돌하면 어떤 조항과 지시가 충돌하는지 표시한다. Agent가 조용히 무시하거나 임의로 규칙을 바꾸지 않는다.

**착수 계약 제안:** 작업 묶음에는 목적/이번 작업 이유, 헌법 버전, 최신 관련 지시, 확정 결정과 이유, 설계·계획 버전, 이미 완료한 것, 임무·허용/금지·완료 조건·환경을 반드시 포함한다. 생략된 대화는 검색 가능한 원문 참조를 제공한다. 전달할 자료는 사용자 소유 자료이므로 외부 도구별 전송 범위도 연결 설정의 허용 대상과 대조한다.

### 6.2 이해와 행동 대조

- 새 총괄/단계 세션은 ‘목적, 핵심 규칙, 현재 위치, 변경하지 말아야 할 결정, 이번 실행 범위, 다음 행동, 모르는 부분’을 먼저 되짚는다.
- 총괄 교체는 사용자, 단계 세션은 총괄이 기준과 대조한다. 단순 읽음 체크나 파일 hash만으로 이해 합격을 처리하지 않는다.
- 실행 전에는 대상 경로·환경·권한·기준 버전·쓰기 소유권을 검사한다. 제어 가능한 명령은 허가 범위 밖이면 전달하지 않는다.
- 실행 후에는 변경 파일/산출물/증거를 설계·허용 범위와 대조한다. 위반 발견은 해당 결과 보완/격리와 관련 실행 정지 사유가 된다. 무관한 작업 전체를 자동 폐기하지 않는다.
- 외부 Agent가 도구 내부에서 수행하는 모든 행동을 Anvil이 완벽히 차단한다고 약속하지 않는다. 직접 제어/실행 격리/사후 관측 중 어떤 수준인지 표시한다. 필요한 통제를 보장하지 못하면 해당 위험 작업 배정을 막는다.

### 6.3 미수행·거부·오류 구분

| 판정 | 필요한 근거 | 화면의 다음 행동 |
|---|---|---|
| 승인·입력 대기 | 실제 요청 ID·사유·대상·현재 단계 | 요청 확인·응답 |
| 도구 오류 | 반환 오류·종료 코드·시각 | 오류 상세·허가 범위 재시도·교체 |
| 수행 거부 | 도구가 명시한 거부 결과와 원문 | 원문·대체 도구 선택. 내부 사유 추측 금지 |
| 연결 단절 | 수신 중단·마지막 회수 시각·접속 관측 | 재접속·상태 대조·교체 |
| 원인 미확인 | 응답/관측 부족 또는 모순 | 확인된 지점·빠진 기록·읽기 확인·교체 |
| 완료 주장/증거 불충분 | 제출 내용과 실제 누락의 비교 | 보완 요청·완료 보류 |

‘허위 완료’는 근거 없는 고의 추정이 아니라 완료 주장과 실제 결과의 불일치로 먼저 표시한다. 정상 장시간 명령·기준 내 진행·실제 승인 대기를 방치로 오인하지 않는다.

## 7. 총괄·단계책임자와 작업 실행

### 7.1 AV3-F07 임무·세션 배정 (INT-09,12~16)

사용자가 단계 목적/기대 결과를 입력하면 총괄이 기준 문서에서 세부 임무·대상·완료 조건을 작성한다. 사용자가 수정·확정한다. 반복 임무는 확정한 방법론과 승인 범위 안에서 자동 구체화하되 새 요구를 추가하지 않는다.

단계별 다른 Agent를 지정할 수 있다. 책임자는 직접 수행 또는 하위 Agent 분해를 결정하고 작업 방법을 남긴다. 하위 임무에는 상위 범위·권한의 부분집합만 부여한다. 같은 파일 집합의 writer는 하나다. 겹치는 작업은 대기시키거나 비충돌 범위로 분할한다. 별도 작업 공간을 쓰더라도 통합 책임과 검사 순서를 지정한다.

단계가 끝나거나 재작업할 때 같은 세션을 유지하는 것이 기본이다. 사용자 교체는 언제든 가능하다. 세션이 없어졌다는 이유로 단계·지식·근거를 삭제하거나 처음부터 다시 하지 않는다.

### 7.2 AV3-F08 실행 모드와 시작 조건

| 구분 | 자동 진행 | 건별 진행 |
|---|---|---|
| 사용자 시작 범위 | 선택 단계~정한 종료/승인 지점 | 선택한 단계 한 개 |
| 내부 작업 | 승인 범위 안 책임자 결정 | 동일 |
| 결과 판정 | 총괄이 증거 대조 | 동일 |
| 다음 단계 | 선행·권한 충족 시 진행 | 사용자 다음 지시 전 대기 |
| 승인 지점/위험 작업 | 지정 승인 필요 | 동일 |

시작 전 검사: 현재 작업 사용자/클라이언트 권한, 유효한 기준 문서·입력, 연결 도구의 필수 기능, 환경 준비, 완료 조건, 권한, 기존 실행/쓰기 충돌, 실행 한도. 실패 항목별로 수정할 화면을 연결하며 ‘시작 불가’만 표시하지 않는다.

자동 동작은 사용자 정의 한도·기계적 조건 범위다. 비용/시간 수치를 임의 기본값으로 무제한 처리하지 않는다. 사용자 변경·중지·승인 필요 시 해당 실행을 멈추고 가능한 독립 작업은 계속한다.

### 7.3 AV3-F09 실행 상태·결과 판정 (INT-17~19)

기본 상태 전이는 준비 전→준비됨→배정 대기→시작 요청→수행 중→결과 제출→검토/테스트→완료다. 보완 필요는 원인·범위·재작업 대상과 함께 준비 단계로 돌아간다. 승인/입력 대기, 실패, 중지 요청, 중지 확인, 상태 미확인은 별도 상태로 보관한다.

요청 수락과 실제 수행을 구분한다. 명령·파일·시험 결과의 관측 시각을 표시한다. Agent 보고 상태와 실행기 관측 상태가 다르면 둘 다 보여주고 대조를 요청한다.

완료 판정에는 기준 버전, 변경 파일/diff, 수행 명령·종료 코드·결과, 실행 환경, 정상/중요 실패 확인, 미실행, 잔여 위험을 포함한다. mock·문법·빌드만 통과한 결과를 실제 저장·Agent 실행·배포 완료로 승격하지 않는다. 부족하면 필요한 범위만 보완한다.

일반 보고는 중지 이유가 아니다. 차단 보고는 원인·영향·필요 결정·계속 가능한 작업을 가진다. 동일 문제 자동 시도는 오류 fingerprint와 실제 횟수로 묶되 quota·권한·통신과 기능 실패를 섞지 않는다. 설정한 한도에 도달하면 선택지를 제시한다. 사용자 즉시 교체는 횟수와 무관하다.

### 7.4 AV3-F10 중지·재개·비상 기록 (INT-20~22)

중지 대상은 현재 세션 / 단계와 하위 Agent / 프로젝트 전체다. 접수 즉시 해당 범위 새 배정을 막고 지원되는 중지를 요청한다. ‘요청함’과 ‘실제로 멈춤’을 따로 표시한다. 중지 지원 없음/확인 불가는 원인 미확인 상태로 남기고 새 writer를 시작하지 않는다. 강제 프로세스 종료나 서버 재시작을 자동 대안으로 쓰지 않는다.

재개는 사용자 요청 후 기준·파일·Git·프로세스·이미 제출된 결과를 대조하고 마지막 미완료 지점에서 시작한다. 완료 작업 재실행은 변경 영향이나 근거 부족 사유가 있을 때만 명시한다.

**책임자 상세 작업현황 파일 계약 제안:**

| 구획 | 반드시 저장할 내용 |
|---|---|
| 식별/기준 | 프로젝트·단계·작업·실행/세션, 목적, 문서/계획/헌법 버전 |
| 진행 | 확인 완료, 진행 중 세부 지점, 다음 작업, 남은 작업 |
| 실제 변경 | 파일·diff/commit, 미커밋·비추적, 실행 위치·관련 프로세스 |
| 검증 | 정확 명령·환경·종료·증거 위치, 실패·미실행 |
| 오류 | 동일 문제 식별자·시도·원인 확정/추측·조치·결과 |
| 복구 | 마지막 서버 수신 시각, 로컬 미전송 기록, 승인 대기, 안전한 재개/금지 행동 |

착수·중요 변경·시험·오류·중단 전에 갱신한다. Agent가 기록하지 않아도 실행기는 관측 가능한 대화/실행/파일 증거를 계속 회수하고 기록 누락을 표시한다. 파일 생성만으로 최신 상태를 보장하지 않으며 마지막 회수 시각과 실제 대조 결과를 함께 둔다.

## 8. 지식 보관·학습·도구 이전

### 8.1 AV3-F11 지식 원본과 선별 (INT-23~26)

원문 대화와 구조화 지식을 함께 보관한다. 원문은 발언·지시·오류·판단의 출처이고 구조화 지식은 빠른 재사용 수단이다. 요약을 수정해도 원문이 덮어써지지 않는다. 비밀은 수집 시 차단/마스킹하고 ‘마스킹된 원문’임을 표시한다. 내부 추론 비공개 자료를 수집한다고 주장하지 않는다.

지식 레코드: ID, 종류(목적/헌법/결정/사실/가설/실패·해결/주의), 내용, 출처 위치, 이유, 적용 범위, 확정 주체, 버전, 유효/대체/사용 제외, 관련 설계·작업·증거. 총괄이 중요도·재사용 가능성을 제안한다. 사용자가 정정/제외하며 충돌은 최신 사실 확인 없이 합치지 않는다.

임무에 전달하는 맥락은 목적·헌법·현재 지시·현재 위치의 필수 묶음에 관련 결정/실패/문서를 더한다. 용량 초과면 누락 범위를 표시하고 분할 전달·검색 경로를 제공한다. 핵심 규칙을 조용히 잘라내지 않는다. 검색 결과는 원문 링크와 함께 주고 추측을 사실로 승격하지 않는다.

‘학습’은 프로젝트 경험의 구조화·검색·재사용을 뜻한다. 자체 모델 학습을 필수 전제로 하지 않는다. 다른 프로젝트/사용자 공유와 방법론/헌법 개선의 실제 적용은 사람이 승인한다. 프로젝트 내 검색만으로 외부 공유에 동의한 것으로 보지 않는다.

### 8.2 AV3-F12 최소 손실 이전 (INT-27~29)

| 순서 | 입력·처리 | 저장·확인 결과 |
|---|---|---|
| 1 기록 동결 | 서버 기록 + 실행기 미전송 + 실제 소스 상태 확인 | 인계 기준 시점과 회수하지 못한 범위 |
| 2 실행 정리 | 기존 세션/하위 작업 중지·쓰기 권한 회수 | 확인됨/미확인, 새 writer 허용 여부 |
| 3 인계 내용 확인 | 목적·헌법·지시·이유·문서·상태·실패·증거 선별 | 원문 참조, 비밀 제외, 부족 기록 목록 |
| 4 대상 선택 | 같은 Agent 새 세션 / 다른 Agent / 다른 계정 | 필수 기능·인증·환경 지원 검사 |
| 5 이해 대조 | 새 세션의 이해·실제 파일/Git/프로세스 대조 | 일치/불일치/재확인 사항과 근거 |
| 6 재개 확인 | 총괄 교체는 사용자, 단계 교체는 총괄 | 새 책임 연결·재개 지점·이전 이력 |

새 도구가 확정 결정을 뒤집으면 변경 이유/승인 없이 다음 단계로 진행하지 않는다. 완료 작업을 다시 제안하면 기존 증거를 제시해 불일치를 수정한다. 실제 소스가 기록 이후 바뀌었으면 차이를 새로운 미확인으로 분리한다.

기존 도구 무응답 시 마지막 체크포인트 이후 구간은 ‘회수 공백’이다. 공백을 0으로 꾸미지 않고 복구 가능한 파일·명령 결과와 부족한 판단을 분리한다. 필요한 사용자 보완을 한 곳에 모으고, 모든 설명을 처음부터 다시 요청하지 않는다.

인계 손실 평가 제안: 누락된 필수 항목, 번복된 확정 결정, 불필요한 완료 작업 재실행, 사용자 추가 설명 항목·시간, 현재 위치 오판, 마지막 회수 이후 공백. 수치 임계값은 아직 사용자 확정 전이다. 무단 쓰기·비밀 노출·권한 우회는 ‘허용 가능한 손실’로 다루지 않는다.

## 9. 도구·환경·권한·사용자 인계

### 9.1 AV3-F13 연결 기능 계약 (INT-30~33)

연결 등록은 이름, 유형(설치형/CLI/웹서비스), 실행기, 제공업체 계정 참조, 제품·버전, 지원 모델·옵션·한도를 받는다. 비밀값은 보호 저장소에 두고 일반 화면/문서/로그는 참조만 가진다.

| 기능 | 확인 방법·배정 제약 |
|---|---|
| 실제 작업 지시·세션 생성 | 실행 ID/세션 ID 수신 및 작은 실제 작업 결과 확인 |
| 상태·진행 수집 | 지원 이벤트/조회와 마지막 관측 시각 표시 |
| 결과·실제 파일 회수 | 메시지 외 변경/명령/시험 증거 연결 |
| 추가 지시·중지 | 지원 여부 및 요청/실제 정지 구분 |
| Anvil 세션 재개 | 같은 세션 재연결 또는 새 세션 인계의 차이 표시 |
| 도구 자체 승인 | 공식 인터페이스가 지원하는 동일 요청 응답 연결 |
| 하위 Agent | 실제 노출되는 임무·식별·결과만 표시, 추측 생성 금지 |

각 기능은 확인/미확인/미지원과 검증한 버전·시각을 가진다. 화면 열기만 가능한 연결은 실행용으로 선택할 수 없다. 안전 중지·증거 회수·통제가 해당 임무에 부족하면 배정을 막고 무엇이 부족한지 설명한다. Codex·Claude Code는 대상 예시이며 지금 지원 검증이 끝났다는 뜻이 아니다. 공식 연동 방식·각 버전의 API/CLI 계약은 개별 검증 후 확정한다.

사용 한도 소진과 Anvil 장애를 구분한다. 계정/모델 변경은 지원 범위 안 사용자 선택으로 처리하고 원문·프로젝트 기록을 유지한다. 외부 Agent 승인을 Anvil 승인으로 위조하거나 자동 우회하지 않는다.

### 9.2 AV3-F14 환경·권한

환경은 개발/테스트/배포 용도, 소스 위치, Agent 실행 위치, 빌드·시험 대상, 명령 정의, 도구 버전 요구, 서비스·자격증명 참조, 허용·금지 대상을 가진다. Windows에서 Agent가 실행되며 WSL에서 시험하는 경우 두 위치를 함께 보인다. 환경 연결 시험은 읽기 전용 상태 확인과 실제 변경 시험을 구분한다.

권한 표는 파일 편집, 테스트, 패키지 설치, commit, push/PR/병합, DB schema/데이터, 배포, Secret/인증서, 외부 전송·비용을 대상으로 ‘자동 허용 / 실행 전 승인 / 금지’를 지정한다. 경로·환경·명령 대상·유효기간·상한을 함께 제한한다. 단순 와일드카드로 모든 위험 행동을 허용하지 않는다.

승인 요청은 요청 ID, 정확 대상/범위, 이유, 영향, 비용/데이터/중단 위험, 복구 방법, 기준 버전·만료를 가진다. 이번만 승인/거절/수정 지시가 가능하다. PC·모바일은 같은 요청을 처리하고 한 번 결정된 요청은 재사용할 수 없다. 범위·버전이 바뀌면 이전 승인으로 실행하지 않는다.

### 9.3 AV3-F15 사람·클라이언트 제어권 (INT-35~38)

한 프로젝트에는 한 명의 작업 사용자와 하나의 활성 제어 클라이언트만 둔다. 다른 화면은 조회 가능하고 제어권 인수를 요청한다. 동일 사용자 PC→모바일 전환도 인수로 처리한다. 전체 프로젝트 실행을 중단하는 것과 제어 화면만 바꾸는 것을 구분한다.

다른 사람 인계: 요청→안전 대기→진행·미결·권한 표시→다음 사용자 수락→이전 권한 회수/새 권한 발급. 미수락이면 기존 권한이 조용히 넘어가지 않는다. 권한 없는 사용자는 요청·문서 URL을 알아도 조회할 수 없다. 멤버 추가·공유는 소유자가 결정한다.

한 사용자가 여러 프로젝트를 진행할 수 있다. 전체/프로젝트 한도에 따른 실행 대기열에서 대기 이유·현재 점유·취소를 보여준다. 승인 대기와 실제 수행 슬롯 점유를 구분하며 지원하지 않는 중단으로 슬롯이 풀렸다고 가정하지 않는다.

## 10. 데이터·명령·복구 계약

아래는 기능을 실제 연결하기 위한 논리 설계다. DB 제품·물리 스키마·네트워크 포트·SDK 선택이나 migration 실행 지시가 아니다.

### 10.1 저장 단위

| 개체 | 주요 필드·관계 | 보존 원칙 |
|---|---|---|
| 프로젝트 | 소유자·목적·참여자·상태·현재 기준·현재 위치 | 도구 계정과 독립 |
| 방법론/노드/연결 | 공통/전용·버전·조건·문서 양식 | 적용한 버전 고정 |
| 문서/버전/설계 항목 | 원본·hash·출처·편집자·검토·확정 | 확정 버전 불변 |
| 계획/작업/추적 연결 | 설계 버전·화면/기능/연결 유형·의존 | 과거 코드·시험 링크 유지 |
| 헌법/지시/결정/지식 | 원문·이유·유효 범위·대체 관계 | 원문과 요약 분리 |
| 책임 배정/도구 세션 | 역할·도구·환경·허가 범위·현재 세션 | 세션 종료에도 역할 이력 유지 |
| 실행/관측/산출물/시험 | 요청·관측 구분·명령·종료·증거·기준 | 실패/미실행도 보존 |
| 승인/제어권/쓰기 권한 | 대상·버전·결정·유효기간·세대 번호 | 중복/만료/옛 권한 실행 거부 |
| 체크포인트/인계 | 기준 시각·상태 파일·실제 차이·공백 | 이전 세션 최종 응답에 비의존 |
| 백업/복구/감사 | 포함 범위·시각·검사·영향·실행자 | 복구 후 권한/진행 재대조 |

관계형 상태와 버전 있는 파일/증거 저장을 조합하는 방식을 제안한다. 첨부물은 해시·크기·소유·접근 권한을 갖고 DB 메타데이터와 연결한다. 모든 것을 거대한 단일 대화 문자열이나 Agent 로컬 폴더로 저장하지 않는다.

### 10.2 사용자 행동 → 처리 → 저장 → 재조회

| 행동 | 처리와 저장 | 성공/실패 응답·다음 조회 |
|---|---|---|
| 방법론 저장 | 제어권·기준 버전 검사→초안 개정 저장 | 저장 버전/오류 항목→같은 초안 다시 열기 |
| 문서 확정 | 필수 내용·참조·수정 제안 처리 확인→확정 버전 | 확정 범위 표시. 실행 자동 시작 없음 |
| 작업 시작 | 준비/승인/권한/충돌/한도 검사→실행 요청 저장→실행기에 전달 | 요청 ID·현재 위치→수신/관측 이벤트 |
| 추가 지시 | 대상 세션·적용 시점·중단 여부 기록→전달 | 전달/수신/미확인 구분→대화 원문 |
| 승인 | 동일 요청·대상·버전·작업 사용자 확인→일회 결정 | 중복이면 기존 결과 반환, 변경이면 새 요청 |
| 결과 제출 | 파일/시험 수신·기준 고정→증거 저장→총괄 검토 요청 | 제출됨 표시, 완료 자동 선언 없음 |
| 도구 이전 | 체크포인트·공백·정지 상태→인계본→새 이해 대조 | 이전 이력·재개 허용/차단 이유 |
| 설계 변경 | 변경 요청→영향→승인→계획 개정 | 변경 이력·영향 작업·기존 결과 구분 |

모든 변경 명령은 프로젝트·현재 사용자/클라이언트·대상 버전·중복 방지 키를 갖는다. 같은 클릭/통신 재시도를 여러 번 실행하지 않는다. 명령 저장 후 전달이 실패하면 동일 명령의 전달 상태를 확인해 재전송하고 새 실행을 만들지 않는다. 결과를 받았는지 알 수 없는 부작용 명령은 자동 재실행하지 않고 실제 상태 대조로 전환한다.

### 10.3 통신·장애·체크포인트

- 실행기는 순번 있는 대화/실행/관측 기록을 로컬에 임시 보존한다. 서버 저장 확인 전 삭제하지 않는다. 서버는 실행 ID+순번으로 중복 수신을 제거한다.
- 화면에는 서버 수신 완료 지점과 실행기 미전송 지점·최신 관측 시각을 보여준다. 타임라인 정렬은 단말 시계만 믿지 않고 서버 수신/실행 순번을 함께 사용한다.
- 탭/창 닫힘은 프로젝트 중지 명령이 아니다. 기존 허가 범위의 백그라운드 작업은 계속하고 승인 지점에서 기다린다.
- 제어 서버 통신 단절 시 진행 중 허가 작업은 기존 범위·기한 안에서만 처리한다. 새 승인·새 단계·범위 확대는 금지한다. 상세 단절 정책은 환경별로 사용자가 검토한다.
- Anvil 완전 종료는 종료 범위의 새 배정을 차단하고 안전 중지/기록한다. 재기동 후 자동으로 새 쓰기 실행을 시작하지 않고 실제 상태 대조와 사용자 재개를 받는다.
- 중지됐는지 불명인 실행, 이전 세대 token, 만료 제어권은 새 writer에 권한을 주지 못한다. 외부 프로세스의 쓰기를 확실히 차단할 수 없으면 격리/대조 전까지 실행 차단을 유지한다.
- 디스크 부족·기록 저장 실패는 숨기지 않는다. 복구 자료를 보장할 수 없는 새 작업은 차단하고 기존 실행의 안전 중지를 요청한다. 미수신 기록 손실은 범위·시각과 함께 표시한다.

### 10.4 백업·내보내기·보존

백업은 원본 문서·버전·지식·대화·승인/실행 이력·첨부 증거·연결 설정의 비밀 제외 참조를 포함한다. 소스 저장소 포함 여부와 미커밋 파일 포함 여부를 명시한다. 외부 Agent 계정 자체와 비공개 세션 내부는 포함하지 않는다. 암호화 키는 백업과 별도 관리하고 자격증명 복원은 재연결 절차로 처리한다.

설정: 백업 위치·주기·보관 기간·암호화·마지막 성공/실패·복구 검사. 정책 수치는 사용자 선택이며 무단 외부 업로드하지 않는다. 복구는 현재 영향과 덮어쓸 범위를 표시하고 사용자 확인 후 실행한다. 먼저 검증용 복원으로 문서/참조/증거 무결성을 확인하며 실행 프로세스는 자동 재시작하지 않는다.

사용자 소유의 이식 가능한 묶음으로 문서(Markdown), 구조화 상태·관계(JSON), 첨부·증거, manifest/hash를 내보내는 방식을 제안한다. Anvil 자체를 옮겨도 특정 Agent 로그인이 원본 조회의 필수조건이 되지 않도록 한다. 삭제·보존 정책은 별도 사용자 결정이며 도구 해제·프로젝트 보관·백업 만료와 혼동하지 않는다.

## 11. 상세 화면 설계와 시안

### 11.1 공통 화면 규칙

아래 SVG는 **이번 상세 설계 검토용 정적 시안**이다. 표시 데이터·인물·상태는 예시이며 실제 Agent 연결·실행·저장 결과가 아니다. 화면 번호/작업 상태 표시는 설계 추적 개념을 보여준다. 정적 배치 검토 뒤 클릭형에서 아래 동작·분기·오류를 연결하고 검토한다. 정적 시안 작성만으로 INT-06의 클릭형 검토 완료를 주장하지 않는다.

PC 기준 1920×1080, 1440×900에서는 패널 폭을 조정한다. 모바일 기준 430×844. 남색 배경·파란 강조·간결한 사이드바를 유지한다. 본문/폼 12px, 메뉴 14px, 제목 16px, 메타데이터 10px. 본문은 sans-serif 한국어 글꼴 fallback을 사용하고 외부 폰트 요청에 의존하지 않는다. 버튼은 PC 높이32px 이상·모바일 터치44px 이상, 모바일 입력 글자16px을 쓴다. 색과 상태 문구를 함께 사용한다. 상세 설명은 i/펼치기로 제공한다.

**화면 지도:** 프로젝트 목록→새 프로젝트 또는 프로젝트 작업. 프로젝트 작업에서 방법론, 문서·설계 추적, 지식·헌법, 도구·환경, 승인, 이전으로 이동한다. Dashboard는 프로젝트의 보조 조회 메뉴다. 기존 관리 메뉴 11개를 그대로 중심에 배치하지 않는다.

공통 상태: 로딩(대상·행동 표시), 빈 목록(작성/연결 행동), 오류(확인된 원인·재시도·기존 입력 보존), 권한 없음(조회 가능 범위·인수 요청), 연결 단절(마지막 동기화·미전송), 미저장(저장/버림/돌아가기), 로그인 만료(입력 임시 보존·재인증), 다른 버전 충돌(비교). 실행/삭제 같은 위험 버튼은 결과와 대상 확인 후 처리한다.

- 검색/상태 필터는 목록만 바꾼다. 행 선택은 S04 총괄 탭으로 이동하며 실행하지 않는다.
- 새 프로젝트→S02. 인수 필요 배지→S12. 결정 요청→S08 해당 요청.
- 빈 상태는 ‘새 프로젝트/방법론 준비’; 로딩 실패는 이전 목록을 오래된 자료로 표시한다. 숨긴 접근 불가 프로젝트의 이름·개수를 노출하지 않는다.

### 11.3 AV3-S02 프로젝트 만들기·기준선

![S02 프로젝트 만들기 정적 시안](assets/av3-s02.svg)

| 단계 | 필드·동작 | 저장/오류/다음 |
|---|---|---|
| 목적·소스 | 이름, 왜 만드는가, 기대 결과, 빈 폴더/기존 소스, 실행기·경로 | 목적 미입력/경로 접근 불가 표시, 임의 폴더 삭제 없음 |
| 방법론·자료 | 공통 버전/전용, 문서 첨부·추출 후보·대화 보완 | 원본 보존·후보 확인, 실행 안 함 |
| 총괄·환경 | 연결 도구·모델·환경·작업 사용자 | 지원 부족은 준비 필요로 저장 |
| 시작 기준 | 기존 소스의 4종 구현 상태·증거·미확인 | 사용자 확인으로 기준선 저장 |

‘프로젝트 생성’은 프로젝트와 입력을 저장해 S04로 이동한다. 실제 작업은 준비 확인과 별도 시작 지시가 필요하다. 중간 저장 후 돌아올 수 있다. 기존 경로는 읽기 조사 전에 범위를 보여주며 민감 파일 내용 수집을 제외한다.

### 11.4 AV3-S03 방법론 흐름도·노드 상세

![S03 방법론 흐름도 정적 시안](assets/av3-s03.svg)

- 왼쪽: 공통/전용·이름·버전. 가운데: 흐름도, 노드 추가(사람/Agent/분기/합류), 연결/재작업, 확대/축소. 오른쪽: 선택 노드 속성(§4.2).
- 노드 선택은 편집 패널만 바꾼다. 드래그/연결은 초안 변경이다. 삭제 전 연결·필수 문서 영향 확인, 실행 중 적용본은 직접 삭제 불가.
- ‘총괄에 구체화 요청’은 목적·결과에서 임무·완료 조건 제안을 만들고 전후 비교를 연다.
- 초안 저장/유효성 검사/확정 요청/프로젝트 적용을 구분한다. 확정 시 미연결·분기조건·완료기준 누락의 해당 노드로 이동한다.
- 사용 중 공통 개정은 영향 목록을 보여주고 유지/프로젝트 적용본 개정 중 선택한다. 실행 중인 프로젝트 자동 변경 없음.

### 11.5 AV3-S04 프로젝트 작업 — 주 작업 화면

![S04 프로젝트 작업 정적 시안](assets/av3-s04.svg)

| 영역 | 상세 구성·동작 |
|---|---|
| 상단 | 프로젝트·목적 바로보기, 현재 단계, 자동/건별·허용 범위, 제어권, 시작/일시정지 |
| 왼쪽 절차 | 단계별 진행 상태·완료/전체 작업, 선택 단계 책임자와 하위 Agent 펼치기 |
| 가운데 세션 | 총괄 기본 탭, 열린 단계 세션 탭 유지, 대화·실행 요약 타임라인 |
| 입력 | 받는 세션 명시, 추가 지시 / 중단 후 지시, 첨부·전송. 전송/수신/반영 여부 표시 |
| 오른쪽 | 현재 단계 기준 문서·작업·코드·결과, 연결된 설계 위치/증거·미확인 |

단계 선택 시 가운데 책임자와 오른쪽 자료가 함께 바뀐다. 총괄 탭으로 언제든 돌아간다. 명령/파일/시험 이벤트를 펼쳐 원문·환경·종료 코드를 본다. Agent 대화와 Anvil 관측을 다른 표식으로 구분한다.

시작→준비 검사 결과/정확 범위 확인→실행 요청. 중지→범위 선택→요청/실제 정지 표시. 재개→기록/실제 차이 확인. 조회자는 입력·실행·승인 비활성, 인수 요청 제공. 연결 끊김은 전송되지 않은 지시를 ‘수신됨’으로 표시하지 않는다.

### 11.6 AV3-S05 단계책임자·실행 상세

![S05 책임자와 실행 상세 정적 시안](assets/av3-s05.svg)

- 상단: 단계 임무·완료 조건·기준 버전·책임 도구/세션, 유지/교체, 허가 범위.
- 작업 방법: 직접/하위 Agent 선택 이유·임무 분해. 하위 목록: 담당·범위·진행·마지막 관측·결과.
- 현재 실행: 요청/수신/관측/결과 시각, 실행 환경, 진행 중 명령, 변경 파일, 시험, 승인 대기. 세션 보고와 실제 관측 차이를 표시한다.
- 탭: 대화/작업현황 파일/변경/검증/원문. 파일은 읽기 비교, 일반 UI에서 임의 서버 명령 실행 화면으로 바꾸지 않는다.
- 보완 요청은 부족 항목·증거와 함께 같은 단계에 연결. 새 세션/도구 교체→S09, 위험 임무 범위 변경→S08.
- ‘완료’ 주장만 있고 결과가 없으면 ‘제출·검증 필요’ 배지. 결과 일부 수신이면 수신된 범위와 누락을 함께 보여준다.

### 11.7 AV3-S06 문서·설계·계획 추적

![S06 설계와 개발 추적 정적 시안](assets/av3-s06.svg)

- 왼쪽 문서 목록: 헌법·요구·설계·계획·테스트·환경·현황. 문서 버전/초안·확정/사용 중을 구분한다.
- 가운데: Markdown/상세 시안. 설계 항목 ID와 시안 위치별 상태 표식 표시, 표식 클릭 시 오른쪽 추적 패널.
- 오른쪽: 연결 화면/기능/연결 작업, 책임 단계·실행, 코드 diff, 시험·증거, 실패/미확인과 최신 판정.
- 직접 편집/총괄 수정 요청→변경 제안. 전후 비교→초안 반영. 기준 적용은 S07 변경 절차.
- ‘설계 확정’은 사용자 결정이며 클릭형 시안 검토·필수 항목 확인을 포함한다. 확정 후에만 작업계획 작성 행동을 활성화한다.
- 계획 보기에서 화면/기능 작업을 분리하고 연결 작업을 명시한다. 설계 연결이 없는 작업/계획 없는 설계는 누락 목록으로 보인다.

### 11.8 AV3-S07 설계 변경·영향·이력

![S07 설계 변경 정적 시안](assets/av3-s07.svg)

입력: 변경 이유·요청자·전후·연결 ID. 영향 표: 관련 화면/기능/계획/진행/완료 결과/시험/권한, 영향 있음/없음/미확인과 근거. 사용자는 적용 승인/거절/수정 지시를 선택한다. 영향 불명은 자동 무영향 처리하지 않는다.

승인 후 계획 개정 상태를 표시하며 개정 완료 전 영향 작업 재개는 비활성이다. 이력 탭에서 버전 비교·원결정 이유·승인·관련 commit/시험을 조회한다. ‘변경됨’은 기존 완료 결과를 삭제한다는 뜻이 아니다. 잘못된 적용 실패 시 기존 기준 유지 및 부분 반영 범위를 표시한다.

### 11.9 AV3-S08 승인·중요 문제 카드

![S08 승인 요청 정적 시안](assets/av3-s08.svg)

카드: 누가 무엇을 요청했는가, 대상 프로젝트/단계/환경, 이유, 정확 변경 범위, 데이터/보안/비용/중단 영향, 복구 방법, 기준 버전·만료, 근거 펼치기. 이번만 승인/거절/수정 지시. 묶음의 무관 요청을 한 번에 승인하지 않는다.

승인 버튼은 현재 작업 사용자·제어권·미결 요청일 때만 활성이다. 다른 기기에서 결정되면 완료된 결정과 시각을 표시한다. 거절은 해당 요청만 거절하며 프로젝트 삭제/전체 중지로 해석하지 않는다. 수정 지시는 원요청 이력을 남긴 새 요청으로 연결한다. 알림 클릭만으로 승인하지 않는다.

원인 미확인 문제 카드는 마지막 요청/수신/수행 지점·빠진 기록·읽기 확인/교체 선택을 제공한다. 확인되지 않은 내부 원인을 만들어 보여주지 않는다.

### 11.10 AV3-S09 세션·도구 이전

![S09 도구 이전 정적 시안](assets/av3-s09.svg)

4단계 화면: 기록/안전 상태→인계 내용→대상 도구/새 세션→이해 대조/재개. 각 단계에서 목적·헌법·결정 이유·완료/미완료·실제 차이·공백이 보인다. 이전 대상이 총괄인지 단계인지 명시한다.

기존 도구 정지 미확인 시 붉은 상태와 진행 중 대상, ‘읽기 인계 준비 가능/새 쓰기 불가’를 표시한다. 대상 기능 부족은 부족 기능을 보여주고 선택을 막는다. 새 세션의 이해에 불일치가 있으면 관련 원문을 열어 보완하고 완료로 넘기지 않는다.

재개 버튼은 안전 정지·필수 기능·실제 상태 대조·확인 주체 조건 충족 후 활성이다. 기존 도구 응답이 없더라도 축적 기록으로 진행하고 공백은 명시한다. ‘연결 해제’는 프로젝트/지식 삭제와 분리한다.

### 11.11 AV3-S10 헌법·지식·결정 이유

![S10 헌법과 지식 정적 시안](assets/av3-s10.svg)

종류 탭: 목적·헌법/최신 지시/결정/실패·해결/기타 지식/대화 원문. 목록은 제목·사실/가설·유효/대체/사용 제외·적용 범위·출처. 검색은 허용 프로젝트 안에서만 수행한다.

항목 선택 시 내용·왜 결정했는가·원문 해당 발언·관련 설계/작업·수정 이력. 정정은 이유·새 내용·전후를 기록하고 이전 원문을 숨겨 덮어쓰지 않는다. 사용 제외는 이후 임무 선별에서 빼되 역사/감사 보존과 구분한다. 외부 공유→대상/공유 내용 확인→사용자 승인. 총괄 추천만으로 공유하지 않는다.

헌법 탭에는 현재 실행 적용 버전과 다음 개정 초안을 구분하고 ‘어느 세션에 어떤 버전을 전달/이해 대조했는가’를 조회한다.

### 11.12 AV3-S11 도구·환경·권한

![S11 도구와 환경 정적 시안](assets/av3-s11.svg)

도구 탭: 설치형/CLI/웹서비스, Windows 실행기, 인증 상태(비밀 참조만), 실제 지원 기능 표, 검증 버전·시각, 사용 한도·모델·옵션. 등록/읽기 연결 확인/작은 실제 검증/연결 해제를 구분한다. 실제 검증이 파일을 바꾸면 대상·허가를 먼저 확인한다.

환경 탭: 개발/시험/배포, 소스 위치, Agent 실행기와 실제 대상, 명령/도구, 비밀 참조, 허용·금지. 권한 탭: 대상별 자동/승인/금지, 경로·환경·유효 범위. 저장은 설정 개정이고 이미 진행 중 실행에 조용히 확장 적용하지 않는다. 비밀 원문·내부 주소는 일반 목록이나 브라우저 코드에 노출하지 않는다.

### 11.13 AV3-S12 작업 사용자·클라이언트 인계

![S12 사용자 제어권 정적 시안](assets/av3-s12.svg)

현재 담당자/제어 기기, 조회 참여자, 인수 요청과 사유, 진행 작업·미결 승인·정지 확인을 표시한다. 현재 담당자는 안전 대기 준비, 다음 담당자는 인계 요약 확인/수락을 한다. 완료 전 새 사용자 버튼은 실행 권한을 갖지 않는다.

같은 사용자 다른 기기 전환은 작업을 처음부터 재시작하지 않는다. 기존 제어 클라이언트는 읽기 화면으로 바뀐다. 연결 단절이나 오래된 화면의 승인은 서버 권한 검사를 통과하지 못한다. 인수 실패는 권한 상태를 재조회하고 양쪽 모두 쓰기 허용으로 복구하지 않는다.

### 11.14 AV3-S13 모바일 작업·승인

![S13 모바일 정적 시안](assets/av3-s13.svg)

기본 대화 화면, 상단 프로젝트/현재 역할/제어권, 하단 대화·절차·문서/결과·승인 탭. 역할 전환으로 총괄/단계책임자 선택. 입력은 추가 지시/중단 후 지시를 구분한다. 승인 상세는 PC와 같은 요청 ID·범위·버전을 사용한다.

조회 기기는 인수 후 지시/승인 가능. 작은 화면에서 내용 일부를 숨긴 채 승인하게 하지 않고 영향·범위를 펼쳐 확인한다. 흐름도·상세 설계·계획 편집은 PC 안내와 총괄 수정 요청을 제공한다. 푸시 지원/허가 상태를 표시하고 미지원이면 앱 내 알림 확인으로 구분한다.

### 11.15 AV3-S14 설정·백업·보조 Dashboard

![S14 설정과 복구 정적 시안](assets/av3-s14.svg)

설정: 참여자 권한, 전체/프로젝트 실행 한도, 중요 알림, 백업 위치·주기·보관·암호화 참조, 마지막 성공/실패·복구 검사. 백업 상세에서 포함/제외 파일·시각·검증을 확인한다. 복구는 영향 비교와 사용자 확인 후 실행하며 실행 세션을 자동 재개하지 않는다.

보조 Dashboard는 현재 단계·진행 중·필요 결정·확인된 오류·다음 행동의 요약과 원화면 링크만 제공한다. 주 작업 화면을 대체하거나 임의의 조합·기간 지표를 제품 중심으로 추가하지 않는다. 완료/보관은 사용자 최종 확인 후 처리하고 미완료 종료는 별도 표기한다.

## 12. 보안·품질·설치·운영

### 12.1 즉시 지켜야 할 안전 경계

- 프로젝트별 인증·조회·명령 권한을 서버에서 검사한다. URL/화면 숨김만으로 보호하지 않는다.
- 입력 문서·저장소·외부 도구 응답은 자료다. 문서 안 명령이 사용자 지시나 승인 권한을 획득하지 않는다.
- Secret은 보호 저장소에 두고 전송/표시/기록을 최소화한다. 외부 Agent에 어떤 자료를 보낼지 연결 범위로 제한한다. 감사 원문에도 인증정보를 그대로 남기지 않는다.
- Windows 실행기는 서버와 인증된 연결을 사용하고 소스 경로·심볼릭 링크·허가 범위를 확인한다. 임의 시스템 경로·운영 자원 접근을 기본 허용하지 않는다.
- 브라우저는 same-origin 경로를 사용한다. 내부 API 호스트·localhost·Docker 주소를 클라이언트에 넣지 않는다. 원격 접속은 준비된 HTTPS/VPN 경로에서만 설정한다.
- 사용자 취소/중지, stale 승인, 이전 세션 token, 동시 writer 방지를 시험한다. 안전 통제가 부족한 Agent는 위험 임무에 배정하지 않는다.
- 삭제·복구·권한·외부 비용·공개 배포는 대상과 영향에 맞는 승인 절차를 유지한다. 클라우드 이전은 운영 공개 승인이 아니다.

### 12.2 제품 형태와 설치 흐름

서버 초기 설정: 저장 위치·사용자 인증·백업·접속 경로 확인→Windows 실행기 등록→Agent 실제 지원 확인→프로젝트 준비. 설치형은 이 서버의 동일 프로젝트를 보여주고 로컬 실행기와 연결한다. 설치형 프레임워크·패키징 기술은 아직 선정하지 않았다.

기본은 비공개·실행 전 준비 필요·외부 공개 꺼짐·지원 미확인 도구 배정 불가다. 업그레이드 시 설정/자료 백업·호환성 검사·실행 안전 대기·복구 경로를 제공한다. 사용자에게 내부 Python/DB 명령을 직접 실행시켜야만 일상 운영되는 제품으로 만들지 않는다.

### 12.3 성능·접근성·관측

긴 대화/로그는 페이지 단위·점진 조회하며 원문 검색과 현재 실행 위치를 유지한다. 첨부 수집 실패가 대화 성공으로 숨겨지지 않게 별도 상태를 둔다. 용량·지연·보관량 목표치는 실제 Agent 기록량/사용자 환경을 측정해 작업계획에서 수치화한다. 근거 없이 지연 수치를 확정하지 않는다.

키보드 이동·명확한 focus·label·오류 연결·명도 대비를 적용한다. 본문 대비4.5:1, 중요 UI 경계3:1을 목표로 검증한다. 상태는 색 외 문구/아이콘, 진행 변화는 보조기기에 전달한다. 모바일은 3열 PC를 축소하지 않고 탭으로 나눈다.

관측 기록에는 프로젝트·단계·명령·실행·기준 버전·수신/관측 시각·오류 지점을 연결한다. 서비스 건강과 사용자 작업 성공을 구분한다. API health 성공으로 실제 Agent 수행·저장·인계를 완료 처리하지 않는다.

### 13.3 단계별 구현·검증 원칙

첫 단계는 로컬·WSL에서 기능 전체를 실제 사용 가능한 연결로 구현한다. 화면/API/저장의 일부, 목업·TODO·임시 응답은 구현 완료와 구분한다. 매 작업은 영향 범위의 빌드/문법/핵심 정상·중요 실패를 확인하고 동일 기준의 불필요한 전수 반복을 하지 않는다. 보안·권한·데이터 위험은 미루지 않는다. 연결 불가 기능은 미확인으로 남기고 독립 구현은 계속한다.

Oracle 이전은 별도 승인 후다. 전체 통합/회귀·성능·부하·브라우저/기기·장애복구 정밀 확인을 시행한다. 1단계에서 하지 않은 시험을 이미 통과했다고 쓰거나 기능 누락을 ‘추후 테스트’로 숨기지 않는다. 새 작업계획은 이 설계와 상세 시안 검토 후 별도 작성하며 화면 작업과 기능 작업을 분리·세분화한다.

### 13.4 검토가 필요한 기술 선택·외부 미확인

| 항목 | 현재 상태·결정 시점 | 결정 전 제한 |
|---|---|---|
| Agent별 공식 연동/모델/중지/승인 | 제품·버전별 실제 검증 필요 | 모든 Agent 지원을 약속하지 않음 |
| 총괄 판단용 모델·설치형 기술 | 비교 후 사용자 검토할 기술 제안 | 특정 도구 원본 종속 금지 |
| 물리 DB/파일 저장·보호 저장소·인증 | §10 논리 계약에 맞춰 세부 기술 선정 | schema·권한·Secret 실행 변경 없음 |
| 인계 손실 임계값·성능 목표 | 대표 이전 사례 측정 후 사용자 확정 | 0손실/임의 수치 합격 주장 없음 |
| 백업 위치/주기/보관·통신 단절 한도 | 사용자 환경별 설정 검토 | 무단 외부 저장·무제한 실행 금지 |
| 모바일 푸시·원격 경로 | 브라우저 지원·허용·접속 환경 검증 | 미지원 상태 표시, 임의 공개 없음 |
| 클릭형 상세 시안 | 이번 정적 시안 검토 다음 산출물 | 정적 그림을 클릭형/제품 완성으로 부르지 않음 |

이 항목들은 구현 누락을 숨기는 표현이 아니라 사용자 합의와 외부 지원 확인이 필요한 경계다. 기술 선택으로 요구 범위·보안·비용·데이터 위험이 바뀌면 별도 승인을 받는다.

### 13.5 이번 개정의 검토 범위와 다음 순서

변경 전: 개념 설명 중심, 상세 화면/필드/실제 처리/상태/추적 계약이 없었다.

변경 후: 사용자 소유 목적을 중심에 두고 F01~F15 기능 계약, S01~S14 화면과 정적 시안, 저장·조회·이력·명령·인계·복구·검증 연결을 작성했다. 합의와 상세 제안·제품 미실행을 구분했다. 이전 초안과 인터뷰 원문은 보존했다.

검토 순서: **핵심 정의→방법론/주 작업/인계 화면→나머지 상세 화면→클릭형 동작·오류 시안→설계 확정→화면/기능별 상세 작업계획·테스트계획→구현 승인**이다. 이번 문서 작성으로 제품 구현·새 Agent 실행·서버 변경·Git 원격 업로드를 시작하지 않는다.
