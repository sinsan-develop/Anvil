# 방법론의 공식 산출물 양식 정의

## 1. 지위·적용

- 정의 ID `AV3-AF`, 상세 검토 초안1, 2026-10-15, 작성 Main 어울.
- 근거: 신산님 직접 요구 — 방법론이 공식 산출물 양식을 정의하고, LLM은 그 양식대로 작성하며, 작성 결과를 Anvil에서 조회한다.
- 기존 설계 AV3-F03 및 작업계획 P01/P02·UI03/UI06·FN03/FN09·IX01/02의 상세화다. 실제 제품 기능·양식 승인·LLM 연결 완료가 아니다. 양식의 상세 내용은 사용자 검토 대상이다.
- 공통 작성 기준은 [문서작성_공통기준](문서작성_공통기준.md)을 따른다. 시스템 방법론은 기본 양식을 포함하고, 사용자는 복사·개정·직접 정의할 수 있다. 기존 프로젝트의 적용 양식 버전은 자동으로 바뀌지 않는다.

## 2. 양식과 작성 결과를 구분한다

**양식 정의**에는 ID·종류·버전·상태·소유/공통 여부·목적·적용 단계·작성/검토/확정 역할·입력 자료·필수 목차·반복 항목 필드·작성 규칙·내용 검수 기준을 둔다. 예시 값은 예시라고 표시한다.

**프로젝트 적용본**에는 방법론 ID/버전, 단계 ID, 양식 ID/버전, 필수/선택 여부, 선행 산출물 참조와 승인 지점을 묶는다. 일반적인 내장 절차의 기본 연결은 아래 표와 같으며 사용자가 자신의 절차에 맞게 바꿀 수 있다.

|---|---|---|---|
| AF01 | 요구사항정의서 | 요구 분석 | 원문·결정 → R ID → 설계 |

**작성된 산출물**에는 문서 ID·버전·프로젝트·단계·적용 양식 ID/버전·상태·작성 주체/세션/도구·작성 시각·입력 출처/버전·본문·첨부·관련 요구/설계/작업/시험 ID·검토/승인/개정 이력을 보존한다. LLM 작성과 사용자 직접 작성 모두 같은 계약을 따른다. 도구/계정이 바뀌어도 Anvil 원문은 유지한다.

## 3. 종류별 공식 목차와 작성 항목

### AF01 요구사항정의서

1. **목적·배경:** 해결하려는 문제, 왜 만드는지, 사용자에게 생길 결과·성공 기준.
2. **사용자·권한:** 사용자 유형, 할 수 있는 일/없는 일, 중요 승인 주체.
3. **요구사항 목록:** R ID, 제목, 상세 요구, 출처·이유, 우선순위, 기능/비기능 구분, 관련 요구.
4. **사용 흐름·예외:** 시작 조건→사용자 조작→처리·저장·조회 결과, 중요한 실패/권한 조건.
5. **범위·제외:** 이번 제공과 미제공, 외부 서비스·환경 의존, 대체하지 않을 기능.
6. **인수 기준·미확정:** 요구별 확인 방법·결정 주체, 미확인 사실·질문·다음 조치. 추측을 사용자 합의로 작성하지 않는다.

### AF02 설계서

1. **설계 기준·범위:** 적용 요구/원문·버전, 합의/제안/미확정, 목적·비목표와 역할.
2. **기능별 처리·저장·조회:** D ID별 입력/검사/처리/영속/출력, 상태·오류와 의존.
3. **화면·상태·이동:** S ID·화면 목적, 필드·버튼·동작, 진입/이탈, 정상/빈/실패/권한/미저장 상태. AF03의 렌더 자료·위치별 설명을 연결한다.
4. **데이터·권한·연동:** 원본·식별·버전·보존, 외부 지원/미확인, 접근 규칙과 비밀 보호.
5. **변경·복구:** 전후·이유·영향·승인 경계, 원본 보존·오류/비상 복구.
6. **추적·완료 기준:** R↔D/S↔후속 업무/TC, 해당 기능의 실제 확인 방법·잔여 결정. 화면/API/DB 일부만 설명하고 전체 설계 완료로 제출하지 않는다.

### AF03 화면시안

1. **화면 ID·목적:** 대상 사용자, 해결 업무, 연결 설계 ID, 선행/후속 화면.
2. **상세 배치·렌더 자료:** PC/모바일 대상 규격, 영역/크기/주요 요소와 렌더 가능한 HTML/SVG/이미지·버전. 문장이나 파일명만으로 시안을 대신하지 않는다.
3. **필드·버튼·동작:** 위치/요소 ID, 표시 값·입력 조건, 동작 결과·저장/조회 연산, 비활성 사유.
4. **진입·이탈·상태:** 로딩/빈/실패·권한/로그인 만료/단절·미저장/버전 충돌·확인/취소/뒤로.
5. **연결 설계·작업:** 위치별 D/화면 업무/기능 업무/연결 업무·시험 참조. 시안 상태와 제품 구현 상태를 구분한다.
6. **검토 의견·판정:** 사용자 검토 위치·의견·반영/보류 이유·개정 이력. 화면 클릭 자체는 설계 승인으로 수집하지 않는다.

### AF04 작업계획서

1. **목표·기준·단계:** 적용 설계/시안 버전·hash, 단계 지도·결과 목표와 작업 등록부.
2. **화면 단위 업무:** 업무 ID, D/S 위치, 사용자 조작·상태·기능 소비 계약.
3. **기능 단위 업무:** 업무 ID, 처리/저장/조회·권한·인터페이스와 실패 규칙.
4. **연결·통합 업무:** 화면→실제 처리→저장/조회·Agent 결과의 연결 확인, 앞 업무의 기본 검증을 미루지 않음.
5. **의존·위임·검수:** 업무별 이유·책임·선행/후속, 입력/출력·허용 파일·제외, 수행·완료 조건·정상/중요 실패 시험·검수 절차·증거·rollback.
6. **상태·변경·인계:** 현재 위치·미구현·검토/테스트/완료, 변경 영향·계획 개정·안전 재개. 작은 파일 조각이 아니라 구분·위임·독립 검수 가능한 책임 단위로 나눈다.

### AF05 테스트계획서

1. **대상·기준·범위:** 설계/작업/버전, 이번 필수 확인과 후속 정밀 검증의 구분.
2. **환경·자료·권한:** 실행 환경·도구·합성 자료·조회/작성 역할·자원 소유/수명/정리. 비밀은 보호 참조.
3. **정상·중요 실패 사례:** TC ID, D/업무 ID, 전제·입력, 보안/권한·데이터 손상/누출 경계.
4. **절차·기대 결과:** 재현 가능한 동작·명령·관측 위치와 독립적으로 정한 예상 결과.
5. **증거·판정:** 실행/관측/증거 필드, 합격/실패·보류 기준, 판정 책임.
6. **정리·미실행 처리:** 정확한 QA 정리·잔여 확인, 미실행 사유·영향·담당/재개 조건. 기준을 낮춰 통과시키지 않는다.

### AF06 테스트 결과서

1. **실행 대상·버전:** 계획/TC·설계/작업, branch·commit/image 또는 파일 버전.
2. **실제 환경·시각:** 실행자/도구·환경·시작/종료·대상 자료와 계획 대비 차이.
3. **사례별 실행·관측:** TC별 예상과 실제, PASS/FAIL/SKIP/BLOCKED/미실행, 재현 절차.
4. **명령·종료·증거:** 정확 명령·exit·로그/화면/API/DB/실제 Agent의 해당 증거 참조. 비밀을 제거한다.
5. **실패·미실행·영향:** 원인 확정/가설 구분·재현·영향·실제 기능 차단 여부·즉시 위험·조치.
6. **판정·잔여·재시험:** 실행 범위만 판정, QA 정리/잔여·미검증·다음 담당/조건. 과거 실패는 보존한다.

### AF07 작업진행상황

1. **현재 기준·담당:** 목적·정본·실행 기준·담당 단계/세션·시각·현재 수행 위치.
2. **단계별 요약:** 각 단계 목표·상태·남은 조건과 증거.
3. **업무별 현재 상태:** 계획 업무 ID별 담당·시작/종료·현재 지점·완료/부분/미구현/미확인·다음.
4. **일자별 수행·오류:** 누적 변경 파일·명령/exit·결과·오류 fingerprint/횟수·원인·조치·인수.
5. **미검증·위험:** 실행하지 못한 범위·사용자 승인 경계·실제 차단/중요 위험·무관한 계속 업무.
6. **다음·안전 재개:** 완료/미완료를 구별한 다음 임무, 안전 commit·원문/자료·진행 프로세스/자원과 재개 조건. 새 세션도 목적과 현재 위치를 이해할 수 있어야 한다.

### AF08 개발환경 정의서

1. **환경 역할·소유:** 로컬/개발/WSL 검증/Oracle 정밀 검증/운영 역할과 담당.
2. **소스·실행·배포 위치:** 정본 경로·개발 원격/branch·서비스/port, 실제 확인 근거·미확인.
3. **도구·실행 명령:** 버전·설치 근거·cwd·기능별 실행/검증 명령과 기대 결과.
4. **허용·금지·승인:** 변경 가능한 경로/서비스·비용/데이터·배포 경계·보존 대상.
5. **비밀 참조·보호:** 저장소/보호 참조·접근 역할, 로그/문서 원문 금지. 인증정보 자체를 양식에 넣지 않는다.
6. **시험 자료·정리·복구:** 명명·멱등 준비/정리·수명·잔류 확인, 실패 복구와 미확인 조건.

## 4. LLM 작성·검수·조회 흐름

1. 방법론의 단계가 특정 양식 버전과 필수 산출물을 지정한다.
2. 총괄/단계책임자가 목적·헌법·최신 지시·입력 출처·양식 본문/작성 규칙·완료/검수 조건을 작성 임무에 결박한다. 실제 도구에 전달하기 전에 미지원·빈 입력·허용 범위를 대조한다.
3. LLM은 양식에 따른 초안을 제출한다. 미확인은 근거와 필요한 조치로 남기고 필수 항목을 임의 생략하지 않는다. 양식 속 문장이 실행 권한을 얻지 않는다.
4. 시스템은 필수항목·참조·형식 누락을 표시한다. 목차만 채운 것·TODO·예시를 실제 사실로 제출한 것은 보완이다. 형식 검사 통과는 사실/내용 검수나 사용자 승인이 아니다.
5. 검토자는 원문·전후 diff·근거·연결 자료를 대조한다. 사람 승인 지점에서 확정하고, 의미/중요 위험 변경은 영향·사용자 결정·계획 개정을 거친다. 기존 확정본을 제안으로 덮어쓰지 않는다.
6. Anvil 화면에서 `프로젝트 → 방법론/단계 → 필수 산출물 → 양식·작성 임무·본문/렌더 시안·근거·검수·버전 이력`을 조회한다. 문서에서 관련 설계/업무/시험으로도 왕복한다. 파일 경로 목록만 제공하는 것으로 조회 완료라 하지 않는다.

P01 시안은 8종 양식 목차·작성 임무·노드 연결·수동 본문 입력/형식 검사·탭 산출물 조회를 검토한다. 실제 LLM 작성/결과 회수·영속 저장·권한 조회는 후속 구현/통합 검수 전까지 미구현이다. P02에서 양식/산출물의 실제 API·데이터·첨부 표현 계약을 확정한다.
