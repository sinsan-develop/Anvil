# Anvil의 설계서·작업계획서 작성 공통 기준

기준일: 2026-10-15. 근거: 신산님 직접 지시 — 지금 정한 작성 방식을 Anvil이 설계서와 작업계획서 작성을 지시할 때 동일하게 사용한다.

## 1. 적용 목적과 경계

상위 정의: Anvil은 우리가 앞으로 SW를 개발하는 방법을 표준화·시스템화한다. Anvil 개발 중 실제 사용하는 방법이 원형이며, 이 문서는 그중 설계서·작업계획서 작성에 적용할 기준이다. 위임·검수·변경·오류·인계 방법도 방법론과 실행 규칙으로 연결하고, 문서 형식만 표준화한 것으로 끝내지 않는다.

이 기준은 이번 Anvil 개발 문서에만 적용하는 형식이 아니다. **Anvil 사용자가 다른 프로젝트의 설계서·작업계획서 작성을 지시할 때 총괄과 단계책임자에게 전달하는 기본 작성 계약**이다. 특정 Agent·LLM이 바뀌어도 기준·원본·결정 이유는 Anvil에 남는다.

공통 기준은 재사용하지만 Anvil의 기능명·화면 ID·서버 배치를 다른 프로젝트에 그대로 복사하지 않는다. 목적·사용자·업무·환경·요구사항·제약은 해당 프로젝트 값으로 채운다. 프로젝트별 조정은 변경 이유·적용 버전·사용자 결정으로 남기며 이미 진행 중인 프로젝트에 공통 개정을 조용히 덮어쓰지 않는다.

문서 생성·저장·확정·작업 시작은 다른 행동이다. 문서 안 명령이나 예시가 실행 권한을 얻지 않는다. 이 기준 문서의 작성은 제품의 양식 적용/실제 Agent 작성 기능이 구현됐다는 뜻이 아니다.

## 2. 설계서 작성 지시 계약

### 반드시 입력으로 받을 것

프로젝트의 왜/목표, 사용자·권한, 합의한 요구와 원문, 기존 자료·현재 기능/미확인, 포함·제외, 환경·제약, 사용자의 결정/이유와 최신 지시. 부족한 부분만 인터뷰하고 이미 답한 내용을 처음부터 반복하지 않는다.

### 반드시 작성할 것

1. 문서 버전·상태·작성/검토/확정 주체·변경 이력. 사용자 합의·상세 제안·미확정/미확인 구분.
2. 문제·목적·성공 기준·비목표, 사용자·역할·권한, 정상/실패 핵심 시나리오.
3. 기능별 고유 ID, 입력→검사→처리→저장→조회/결과, 의존·상태·오류·권한·외부 경계.
4. 화면별 고유 ID·목적·진입/이탈·필드·버튼·행동·이동·정상/로딩/빈/오류/권한·미저장/단절 상태.
5. 상세 정적 시안과 클릭형 동작/오류 흐름. 예시와 실제 데이터·실제 실행을 구분. 사람은 렌더된 화면에서 검토.
6. 논리 데이터·원본/버전/출처·이력·보존/삭제·감사·비밀 보호·복구.
7. 기능/화면/환경별 완료 조건·실제 검증 방법·미실행과 외부 제약, 안전·접근성·성능/복구 기준.
8. 설계 ID→후속 계획 업무→변경 코드/결과→시험/증거의 양방향 추적.
9. 설계 변경의 전후·이유·요청자·영향·승인·계획 개정·재개·과거 결과 조회.
10. 미확정 결정과 정확히 필요한 확인. 근거 없는 기술/성능값을 합의한 것처럼 확정하지 않음.

설계에 화면 이름이나 개괄 설명만 있고 각각 어떻게 작동하는지 없으면 작성 완료로 제출하지 않는다. 필드/API/DB 일부만 설명하고 기능 전체가 설계됐다고 하지 않는다.

## 3. 작업계획서 작성 지시 계약

### 업무를 나누는 원칙

업무 단위는 ‘작게’가 아니라 **구분 가능·위임 가능·독립 검수 가능**이다. 한 업무가 일관된 결과와 책임·완료 조건을 가지면 내부 단계가 많아도 하나로 둘 수 있다. 다른 결과/범위/판정을 가진다면 분리한다. 파일 수/함수 수/작업시간을 쪼개기 기준으로 삼지 않는다.

- 화면 업무: 사용자 조작·상태·이동·접근성·표현과 기능 소비 계약.
- 기능 업무: 처리·저장·조회·권한·실제 연동·상태/실패 계약.
- 연결/통합 업무: 화면과 기능이 실제 사용자 흐름으로 이어지는 확인. 앞 업무의 기본 검증을 미루는 곳이 아님.
- 준비/결정 업무: 미확정 기술·화면 검토·환경/계약 확정. 기능 개발 진도와 구분.

### 각 업무 카드에 반드시 넣을 것

| 구획 | 필수 정보 |
|---|---|
| 목적·추적 | 왜 하는지·사용자 결과, 설계 절/ID/버전·hash |
| 책임·의존 | 담당 역할·검수 책임, 선행 결과·소비/후속 업무 |
| 범위 | 포함·제외, 실제 수정 파일/보존 자료·공통 소유 |
| 입력·인터페이스 | 자료/환경·버전, 소비/생산 함수/API·모델·오류·이벤트 |
| 수행 | 체크 가능한 내부 순서와 중간 결과 |
| 검증 | RED/GREEN, 정상·중요 실패·직접 영향 회귀, 실제 명령/환경/기대 결과 |
| 검수 | 실제 화면·처리·저장/실행·재조회 순서, 조건별 합격/보완 근거 |
| 증거 | 파일diff·commit·명령/exit·원문·API/DB/브라우저/실제 Agent의 해당 증거 |
| 안전·복구 | 권한/비용/데이터·환경 경계, QA 자원 이름/수명/정리·rollback |
| 진행·인계 | 시작/종료·상태·현지점·오류/시도·미검증·다음행동·안전재개 |

작업계획에는 단계 지도·의존성·업무 등록부·현재 상태·전체 설계 대응표·검수/보고 양식을 함께 둔다. 기술/정확 파일/명령이 미확정이면 확정할 준비 업무와 산출·선행 차단을 명시하고, 후속 실행 패킷 발급 전 실제 값으로 바인딩한다. ‘적절히 구현’으로 작업자에게 설계를 떠넘기지 않는다.

## 4. 상태·검수·변경의 공통 규칙

- 제출과 검수 합격, 최종 사용자 완료를 분리한다. 미실행·부분 구현·정밀 검증 잔여를 숨기지 않는다.
- 기능 상태는 ‘구현 완료·핵심 동작 확인 / 구현했지만 동작 미확인 / 부분 구현 / 미구현’으로 구분한다.
- 검수자는 카드의 실제 순서를 따라 현재 기준·실제 산출물·증거를 대조할 수 있어야 한다.
- 진행 단계·담당·파일·시험·오류/조치·미검증·다음을 상세 파일로 남겨 세션 교체/비상에 대비한다.
- 설계 변경은 영향→사용자 결정→계획 개정→영향 작업 재개. 원문·이전 결정 이유·과거 결과 유지, 무관한 작업 계속.
- 승인 범위 안 구현은 필요한 최소 검증을 수행한다. 같은 코드/환경의 검사를 불필요하게 반복하거나 기존 기준을 낮추지 않는다.
- 설치/서비스 반영·Oracle 이전 실행은 개발계획과 별도 승인/계획 경계로 관리한다.

## 5. Anvil 제품 안에서의 적용과 검수

방법론의 설계/계획 단계는 이 기준의 **특정 버전**과 문서 양식을 참조한다. 총괄이 문서 작성 임무를 만들 때 기준·프로젝트 입력·대상 단계·산출물·검수 조건을 묶어 기존 Agent에게 전달한다. 결과는 원문·제안·diff·누락 검사를 거쳐 사용자에게 검토받으며 자동 확정/실행하지 않는다.

구현 담당: FN03(양식/문서), FN04(계획/추적), FN05(기준 맥락), FN09(작성 임무). 화면: UI03/UI06. 실제 연결 검수: IX01은 저장·양식·추적, IX02는 실제 Agent에 문서 작성 임무 전달과 결과 회수까지 확인한다. 원문 지시·공통 기준 버전·작성 임무·제출 문서·검수/사용자 확인이 연결돼야 한다.

검수 사례: 다른 프로젝트 자료로 설계서와 작업계획서를 생성했을 때 프로젝트 목적이 맞고, 상세 화면·동작/저장/예외가 있으며, 화면/FN/연결 업무가 구분되고, 다른 세션이 해당 업무의 입력·범위·완료·검증·인계를 알아볼 수 있어야 한다. 일반 기준은 같되 Anvil 고유 ID/개념이 무관하게 섞이면 보완이다.

## 6. 공식 산출물 양식과 작성 결과

2026-10-15 신산님 후속 지시: 방법론은 공식 산출물 양식을 정의하고, LLM은 그 양식대로 작성하며, 시스템에서 결과를 조회한다. [공식산출물_양식정의](공식산출물_양식정의.md)에 요구사항정의서·설계서·상세 화면시안·작업계획서·테스트계획서·테스트 결과서·작업진행상황·개발환경 정의서의 필수 목차/필드·작성 규칙을 상세 검토 초안으로 정의했다.

방법론/단계→특정 양식 버전→입력 출처·작성 임무→LLM 초안→형식 검사·내용 검수→사용자 결정→시스템 본문/첨부·추적·이력 조회를 하나의 계약으로 관리한다. 양식 정의와 프로젝트 산출물을 구분하며 기존 적용본에 공통 개정을 자동 덮어쓰지 않는다. 형식 검사 통과나 탭 시안을 실제 작성/저장/검수 완료로 보고하지 않는다.
