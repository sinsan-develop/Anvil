## 0. 총평

이전 지적 29개 중 **23개가 해소**(C3 포함: 내장 3종 상세가 P01 승인으로 확정)되었고, 3개(C1, C5, C9)는 기존 합의·근거 부족을 이유로 의도적으로 채택하지 않았으며(타당한 사유), **3개(S3, C7, P3)가 부분 해소**입니다. 보완 방식도 좋습니다. 별도 보완 문서를 두지 않고 설계·계획 본문에 직접 통합했고, 이전 본문은 history로 보존했으며, 승인 범위를 넓히거나 줄이지 않았다고 명시했습니다.

특히 개선이 큰 부분은 다음과 같습니다.

- 안전 기반의 순서: `FN01 → FN11 → FN06 → FN08` (등록부와 카드가 일치).
- 위협 모델 TM01~09, 위험 RK01~10, 이해 대조 6항목, 증거 출처 4분류, 문서 드리프트 규칙, 설계↔업무↔시험 추적표(§13.1.1).

남은 문제는 **새로 생긴 것이 아니라 구조적으로 남은 것** 위주입니다. 착수를 막을 만한 것은 없고, P02/P03 전에 정리하면 좋은 것이 4개입니다(§2의 N1~N4).

## 3. 확인했으나 문제 없던 것

- **의존성 일관성:** 계획 등록부와 FUNCTION_WORK 카드의 선행이 FN01~FN18 전부 일치합니다. FN15→FN13, FN16 선행에 FN15·FN13 포함, FN17 선행 FN10/11/12 등.
- **순환 의존 없음:** 등록부의 선행 그래프에 순환이 없습니다. `FN15(E) → FN13(C)`처럼 모두 앞 Stage를 향합니다.
- **ID 대응:** S01~S14 ↔ UI01~UI14, F01~F15 ↔ §13.1.1, TC01~15 전부 최소 한 업무에 매핑됩니다.
- **hash 정직성:** 설계의 r5 관측 hash(`9EF5…`)와 현재 r6 hash를 구분해 기록하고, 보존본을 "원본 바이트의 재현"이라고 주장하지 않습니다.
- **범위 통제:** "44업무 불변, 새 최종 ID 없음, 기능 축소 없음"을 계획·설계·AGENTS에 일관되게 유지합니다.

## 4. 권장 순서

1. **N2** — IX01에 FN11 선행과 격리·만료·옛 세대 사례 추가 (계획 r6 때 한 줄 수정).

## 5. 검토의 한계

- 설계 r6는 r5 대비 diff 39개 구간을 전부 읽었고, 계획 r5는 전체를 읽었습니다. 카드 4종은 선행 줄과 일부만 대조했으며 본문을 전수 정독하지는 않았습니다. `contracts/` 8종(INTERFACES, DATA_MODEL 등)은 manifest hash 일치만 확인했고 내용은 검토하지 않았습니다.
- "해소"는 문서에 규칙이 반영됐다는 뜻입니다. 구현·실측으로 검증됐다는 뜻이 아닙니다(문서도 같은 선을 긋고 있습니다).
- 읽기만 했고 원본은 수정하지 않았습니다.
